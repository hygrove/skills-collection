# UI 原型（UI Prototype）

在一个单一路由上生成**几个截然不同的 UI 变体**，可由一个悬浮在底部的小工具条切换。用户在浏览器里翻转各个变体，挑一个（或从每个里偷点片段），然后把其余的扔掉。

如果问题关乎逻辑/状态，而非"东西长什么样"，那是错的岔路。用 [LOGIC.md](LOGIC.md)。

## 何时这是对的形态

- "这个页面该长什么样？"
- "在敲定之前，我想先看看这个仪表盘的几个选项。"
- "给设置页试一个不同的布局。"
- 任何用户原本会在脑子里三个模糊模型之间花一整天挑来挑去的时候。

## 两种子形态：强烈偏好子形态 A

当 UI 原型**紧贴着 App 的其余部分**时，才容易评判：真实的页眉、真实的侧栏、真实的数据、真实的密度。一个孤零零的、自有的可丢弃路由是真空：每个变体孤立看都还行。只要有像样的现成页面来承载变体，就默认选子形态 A。只有当原型真的没有近旁的归宿时，才伸手去拿子形态 B。

### 子形态 A：对现有页面的调整（首选）

路由已经存在。变体渲染在**同一路由**上，由一个 `?variant=` URL 搜索参数把关。已有的数据获取、参数和鉴权全都保留。只有渲染层切换。这是默认；除非有具体理由不这么做，否则选它。

如果原型针对某样还没有页面、但*本应自然地活在某页面内*的东西（仪表盘的新区块、设置页的新卡片、现有流程中的新步骤），它仍是子形态 A。把变体挂进宿主页面里。

### 子形态 B：一个新页面（最后手段）

只有当被原型化的东西真的没有现成页面可活进去时才用它（例如一个全新的顶级界面，或一个无法被合理嵌入任何地方的流程）。

按照项目已经在用的任意路由约定，创建一个**可丢弃路由**。不要发明一个新的顶级结构。命名时要明显是个原型（例如在路径或文件名里包含 `prototype-zh` 这个词）。同样的 `?variant=` 模式。

在决心采用子形态 B 之前，先 sanity-check：真的没有现成页面能把它嵌进去吗？一个空的路由会藏起设计问题，而一个充实的路由会把它们暴露出来。

两种子形态下的悬浮底部工具条都是一样的。

## 流程

### 1. 陈述问题并选定 N

默认 **3 个变体**。超过 5 个就不再"截然不同"，开始沦为噪声，所以在那里封顶。

把计划用一行写在原型所在处或文件顶部注释里：

> "设置页的三个变体，通过 `?variant=` 在现有 `/settings` 路由上切换。"

无论用户是否在场反驳，这都管用。

### 2. 生成截然不同的变体

起草每个变体。对每一个都坚持：

- 页面的目的，以及它能访问的数据。
- 项目的组件库 / 样式系统（TailwindCSS、shadcn、MUI、纯 CSS，或随便哪种）。
- 一个清晰的导出组件名，如 `VariantA`、`VariantB`、`VariantC`。

变体必须在**结构上不同**：不同的布局、不同的信息层级、不同的首要操作点（affordance），而不只是不同的颜色。三个微调过的卡片网格不是 UI 原型，那是壁纸。如果两个草稿出来太像，就用明确的"不要用卡片网格"指引重做其中一个。

### 3. 把它们接起来

在路由上创建一个单一的切换组件：

```tsx
// 伪代码，按项目的框架适配
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

对于子形态 A（现有页面）：把所有已有的数据获取保持在切换组件之上；只有渲染出的子树随变体变化。

对于子形态 B（新页面）：`/prototype-zh/<name>` 之下的可丢弃路由挂载同一个切换组件。

### 4. 构建悬浮切换器（switcher）

屏幕底部中央一个小的固定位置条，含三样东西：

- **左箭头**：循环到上一个变体（绕回）。
- **变体标签**：显示当前变体键，如果变体导出的是名字，也一并显示。如 `B (Sidebar layout)`。
- **右箭头**：向前循环（绕回）。

行为：

- 点击箭头更新 URL 搜索参数（用框架的路由器，例如 Next 上的 `router.replace`、React Router 上的 `navigate` 等），这样变体可分享、且重载稳定。
- 键盘：`←` 和 `→` 方向键也能循环。当 `<input>`、`<textarea>` 或 `[contenteditable]` 聚焦时，不要拦截方向键。
- 视觉上与页面区分开（例如高对比的胶囊、微妙的阴影），让它明显不属于被评估的设计。
- 在生产构建里隐藏：把关放在 `process.env.NODE_ENV !== 'production'` 或等价检查上，这样误合入的散落原型不会把工具条发到用户那里。

把切换器放进一个单一共享组件，好让两种子形态都能复用。把它放在项目里共享 UI 所在的位置。

### 5. 交付

把 URL（以及 `?variant=` 键）亮出来。用户会在方便时翻转浏览。有趣的反馈通常是**"我要 B 的页眉加 C 的侧栏"**，那才是他们真正想要的设计。

### 6. 捕获答案并清理

一旦某个变体胜出，捕获答案（哪个变体、为什么），然后按 [SKILL](SKILL.md) 描述的方式捕获原型。把胜者折进真实代码，把其余的挪到可丢弃分支，而非 main：

- **子形态 A**：把胜者折进现有页面；把落败的变体和切换器从 main 中移除。
- **子形态 B**：把胜出的变体提升为一个真实路由；把可丢弃路由和切换器从 main 中移除。

完整的变体集合是一手来源，所以它落在可丢弃分支，而非回收站，因为留在 main 分支里的变体组件和切换器会迅速腐坏、迷惑下一位读者。

## 反模式（Anti-patterns）

- **只在颜色或文案上不同的变体。** 那只是微调，不是原型。真正的变体在结构上有分歧。
- **变体间共享过多代码。** 共享一个 `<Header>` 没问题；共享一个 `<Layout>` 就破坏了重点。每个变体都应能自由地抛弃布局。
- **把变体接到真实的变更（mutation）上。** 只读原型没问题。如果一个变体需要变更，把它指向一个 stub：问题是"它该长什么样"，而不是"后端能跑通吗"。
- **把原型直接提升进生产。** 变体代码是在原型约束下写的（无测试、错误处理最少）。折进去时要好好重写。

# 逻辑原型（Logic Prototype）

一份单一、自包含的 HTML 文件（一个**可分享的 demo**），让任何人都可以通过点击按钮来驱动一个状态模型。当问题关乎**业务逻辑、状态转移或数据形态**时使用：那种在纸面上看着合理、只有拿真实案例推一遍才会觉得不对劲的东西。

因为它是一个无需安装的文件，你可以把它交给非开发者（设计师、PM、领域专家），让他们自己感受这个模型。所以它说的是他们的语言，而不是代码的语言。

## 何时这是对的形态

- "我不确定这个状态机能否处理 X 然后 Y 这种边界情形。"
- "这个数据模型真的能让我表达……这种情形吗？"
- "在写之前，我想先摸清楚 API 应该长什么样。"
- 任何有人想**按按钮、看状态变化**的情形。

如果问题是"它该长什么样"，那是错的岔路。用 [UI.md](UI.md)。

## 流程

### 1. 陈述问题

在写代码之前，写下你在原型化什么状态模型、什么疑问。一个段落，放在 demo 顶部（放在页面顶部一段看得见的引言里，而不只是写在注释里）。一个回答了错误问题的逻辑原型纯属浪费，所以把问题显式写出来，以便日后核对——无论用户现在看着，还是之后离手回来。

### 2. 把逻辑隔离进一个可移植模块

把真正的逻辑（回答那个问题的那部分）放进一个 `<script>` 块，写成一个小的纯模块，日后能整个拎出来丢进真实代码库。它周围的页面是可丢弃的；这个模块不是。

正确的形态取决于问题：

- **一个纯 reducer**：`(state, action) => state`。当动作是离散事件、状态是单一值时合适。
- **一个状态机**：显式的状态和转移。当"此刻哪些动作合法"本身就是问题的一部分时合适。
- **一小撮针对普通数据类型的纯函数**。当没有隐式当前状态、只有变换时合适。
- **一个拥有清晰方法表面的类或模块**，当逻辑确实持有持续的内部状态时。

挑最契合所问问题的形态，*而不是*最容易接到页面上的那个。保持纯粹：没有 DOM、没有 `document`、没有按钮处理器伸进它内部。页面调用它；没有任何东西反向流回。这正是原型在其自身生命周期之外仍有用的原因：一旦问题被回答，被验证过的 reducer / 机器 / 函数集就能自行抬进真实模块。

### 3. 构建可分享的 HTML 文件

一个文件，纯 HTML/CSS/JS：无框架、无打包器、无服务器，一切内联，以便双击打开、经得起被邮件传来传去。任何人应该都能通过打开它来运行。

为非开发者而写。每个标签都用**领域语言**，而非代码：按钮和状态读起来像业务，而不是 reducer。用大白话解释正在发生什么。

用清晰的层级自上而下布局：

1. **标题与一句话解释**：这个 demo 让你可以探索什么（步骤 1 的问题）。
2. **当前状态（Current state）**：完整的相关状态，渲染成一个可读面板（带标签的字段，而非原始 JSON 转储），每次点击后重渲染，使变化可见。在非开发者难以跟随时，点出刚刚变了什么。
3. **自由探索按钮（Free-play buttons）**：每个动作一个按钮，始终可用，任何人都能以任意顺序戳这个模型。每次点击派发其动作并重渲染状态。
4. **引导式走查（Guided walkthroughs）**：一组**场景（scenarios）**，每个一个标签页。每个标签页装着一段简短的、大白话的场景描述（它设置的情形与要留意什么），其下是该场景要按次序**点击的按钮**。每一步都是一个真实的按钮：点击它执行那个动作并进入下一步。开始一次走查会重置到已知的初始状态，这样场景每次都跑得一样。

挑选能展示别扭情形的场景——那些在纸面上难以推理的：happy path、一个棘手的边界情形、一次对"本应非法"之事的尝试。

保持美观但有节制：干净的排版、充裕的间距、一个强调色。不要动画、不要噱头：任何与状态和按钮抢戏的东西都不要。

### 4. 交付

把文件发给他们，或为他们打开它。他们会在方便时点击走查和自由探索；有趣的时刻是当他们说"等等，那不该可能发生"或"咦，我原以为 X 会不一样"——那些是*想法*里的 bug，而这正是重点。如果他们想要新动作或新场景，就加上。原型是会演进的。

### 5. 捕获答案与原型

一旦原型回答了它的问题，先捕获答案，然后按 [SKILL](SKILL.md) 描述的方式捕获原型。逻辑专属的映射：被验证过的 reducer / 机器 / 函数集抬进真实模块（决策，被吸收）；HTML 外壳随被丢弃的分支一起保留，让原型作为一手来源，而它既然是一个自包含文件，在那里就仍可轻松重跑。

## 反模式（Anti-patterns）

- **不要加测试。** 一个需要测试的原型就不再是原型。
- **不要把它接到真实数据库。** 用内存状态，除非问题明确关乎持久化。
- **不要泛化。** 不要"如果我们以后想支持 X 怎么办"。原型只回答一个问题。
- **不要模糊逻辑与页面。** 如果纯模块引用了 DOM、`document` 或按钮处理器，它就不再可抬升。把页面当作纯模块之上的一层薄壳。
- **不要伸手去拿框架、打包器或服务器。** 一个收件人双击就能打开的文件；一个 React 应用或一个 dev server 都破坏了"可分享"。
- **不要把 HTML 外壳交付进生产。** 页面是为被人手点而优化的。它背后的逻辑模块才是值得保留的那块。

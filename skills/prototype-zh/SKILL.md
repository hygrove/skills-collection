# 原型（Prototype）

原型是**用来回答一个问题的一次性代码**。问题决定形态。

## 选分支

判断正在回答的是哪个问题，依据用户的提示、周围的代码，或在用户在线时直接问：

- **"这个逻辑 / 状态模型感觉对吗？"** → [LOGIC.md](LOGIC.md)。构建一个可分享的单 HTML 文件（自由操作按钮 + 分页引导走查），把状态机推过那些在纸面上难以推理的情况，并且非开发者也能驱动它。
- **"这该长什么样？"** → [UI.md](UI.md)。在单一路由上生成几个 radically 不同的 UI 变体，可通过 URL 查询参数和一个浮动的底栏切换。

两个分支产出截然不同的制品，所以搞错分支会浪费整个原型。如果问题真的模糊且联系不上用户，默认选更匹配周围代码的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部写明这个假设。

## 两者都适用的规则

1. **从第一天起就是一次性的，并且明确标为一次性。** 把原型代码放在它真正会被使用的地方附近（紧挨着它为之前景的模块或页面），这样上下文明显；但命名要让随便一个读者都能看出这是原型而非生产代码。对于一次性 UI 路由，遵守项目已有的路由约定；不要发明新的顶层结构。
2. **运行零门槛。** UI 原型从项目 task runner 里的一条命令启动：`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑演示是用户双击就能开的单 HTML 文件。总之，启动它不需要动脑子。
3. **默认不持久化。** 状态活在内存里。持久化是原型*在检验*的东西，而不是它应该依赖的东西。如果问题明确涉及数据库，用一个 scratch DB 或一个名字清清楚楚写着"PROTOTYPE, wipe me"的本地文件。
4. **跳过打磨。** 不写测试、不做超出"让原型能跑起来"的错误处理、不做抽象。重点是快点学到东西。
5. **把状态亮出来。** 每次操作后（逻辑）或每次变体切换时（UI），打印或渲染出完整的相关状态，让用户能看见变了什么。
6. **做完就捕获它。** 把任何已验证的决定折进真实代码，然后把原型本身作为**首要来源**捕获：提交到一个从 main 分出的、一次性的分支，并在实现 issue 上留下指向该分支的上下文指针。也把答案（结论 + 它解决的问题）记录在 issue 或 commit 里。主分支只保留已验证的决定。

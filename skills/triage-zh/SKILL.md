# 分诊（Triage）

把项目问题追踪器上的 issues 推过一套由分诊角色组成的小型状态机。

如果本仓库把外部拉取请求（pull request）当作一种请求入口（参见 issue-tracker 配置），那么分诊也涵盖它们：**PR 就是附带代码的 issue**，使用同样的角色、同样的状态、同样的状态机，下面有几处标记为"针对 PR"的差异。把一个光秃秃的 `#42` 根据追踪器配置解析成 issue 或 PR。

分诊期间发布到问题追踪器的每一条评论或 issue **都必须**以此免责声明开头：

```
> *This was generated by AI during triage.*
（*这是分诊期间由 AI 生成的。*）
```

## 角色（Roles）

两类**分类（category）**角色：

- `bug`：出错了
- `enhancement`：新功能或改进

五类**状态（state）**角色：

- `needs-triage`：维护者需要评估
- `needs-info`：等待报告者提供更多信息
- `ready-for-agent`：已完整描述，可供 AFK（离手）agent 接管
- `ready-for-human`：需要人工实现
- `wontfix`：不会处理

对于 PR，同样的状态对照所附代码来读：`ready-for-agent` 意味着已附简报、agent 应当在 diff 上迈出下一步；`ready-for-human` 意味着它已可供人类合并。

每个被分诊的 issue 应当恰好带一个分类角色和一个状态角色。如果状态角色冲突，先标记出来并询问维护者，再做任何其它事。

这些是规范性角色名。问题追踪器中实际使用的标签字符串可能不同。映射关系本应已提供给你。如果没有，请告诉用户去运行 `/setup-matt-pocock-skills`。

状态转移：一个未打标签的 issue 通常先进入 `needs-triage`；从那里可转移到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告者回复后，`needs-info` 回到 `needs-triage`。维护者随时可以覆盖；对看起来异常的转移请标记出来并在继续前询问。

## 调用（Invocation）

维护者调用 `/triage` 并用自然语言描述他们想要什么。解读请求并执行。例如：

- "把需要我关注的东西给我看看"
- "我们看看 #42"（issue 或 PR）
- "把 #42 移到 ready-for-agent"
- "有哪些已经可供 agent 认领了？"

## 展示需要关注的内容

查询问题追踪器，呈现三个桶（bucket），最旧的在前：

1. **Unlabeled 未打标签**：从未分诊过。
2. **`needs-triage`**：评估进行中。
3. **`needs-info` 且自上次分诊记录以来报告者有活动**：需要重新评估。

当 PR 在范围内时，把这些外部 PR 也纳入这些桶，并给每行打上 `[PR]` 或 `[issue]` 标签。发现（discovery）只暴露*外部* PR（追踪器配置定义谁算外部），因此协作者的进行中 PR 不算分诊工作。这个过滤器只用于发现；被显式点名的 PR 无论作者是谁都会被分诊。

展示计数和每条的一行摘要。让维护者挑选。

## 分诊一个具体 issue 或 PR

1. **收集上下文。** 通读整个 issue 或 PR（正文、评论、标签、作者、日期；对 PR 还要看 diff）。解析任何先前的分诊记录，这样你不会重复问已解决的问题。使用项目领域词汇表探索代码库，尊重该区域的 ADR。对代码库跑两项检查：(a) **冗余性**：按领域概念（不只是请求的措辞）搜索该请求行为的现有实现，并报告你查过哪里。如果找到，这就是一个已实现的 `wontfix`（第 5 步）。(b) **先前拒绝**：读 `.out-of-scope/*.md`，把任何类似此请求的文件摆出来。

2. **推荐。** 告诉维护者你的分类和状态推荐及理由，外加一段与该请求相关的简要代码库摘要（包括是否已实现）。等待指示。

3. **核实主张。** 在任何诘问之前，先检查该主张是否成立。对 bug，按报告者的步骤复现它。对 PR，确认 diff 确实做了它所声称的事：把它 checkout 出来，运行相关测试或命令。报告发生了什么：已确认（附代码路径）、失败、或细节不足（这是强 `needs-info` 信号）。一次被确认的核实会造就一份强得多的 agent 简报。

4. **诘问（若需要）。** 如果请求需要充实，调用 Skill 工具两次，分别传入 "grilling" 和 "domain-modeling"，一次一轮地把问题烤成型，在决策落定时打磨领域术语并就地更新 `CONTEXT.md`/ADR。

5. **落实结果：**
   - `ready-for-agent`：发布一条 agent 简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`：与 agent 简报同样的结构，但注明为何不能委派（判断性取舍、外部访问、设计决策、手动测试）。
   - `needs-info`：发布分诊记录（模板如下）。
   - 对于 `wontfix`，关闭 issue，评论内容取决于*为什么*：
     - **已实现**：该改动已经存在于代码库中。指出它在哪里；**不要**写入 `.out-of-scope/`（那个知识库是给*被拒绝*的请求用的，不是给已构建的）。
     - **被拒绝（bug）**：给出礼貌的解释，然后关闭。
     - **被拒绝（enhancement）**：写入 `.out-of-scope/`，从评论里链接过去，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`：应用该角色。若有部分进展可选择性评论。

## 快速状态覆盖（Quick state override）

如果维护者说"把 #42 移到 ready-for-agent"，相信他们并直接应用角色。确认你将要做什么（角色变更、评论、关闭），然后执行。跳过诘问。如果未经诘问会话就移到 `ready-for-agent`，问他们是否想写一份 agent 简报。

## Needs-info 模板

```markdown
## Triage Notes 分诊记录

**我们目前已确认（What we've established so far）：**

- 要点 1
- 要点 2

**我们还需要你（@reporter）提供什么（What we still need from you）：**

- 问题 1
- 问题 2
```

把诘问期间解决掉的所有内容都记在"目前已确认"下，以免工作丢失。问题必须具体、可操作，而不是"请提供更多信息"。

## 续接上一次会话（Resuming a previous session）

如果 issue 或 PR 上已有先前的分诊记录，就去读它们，检查报告者是否已回答了悬而未决的问题，并在继续前呈现一幅更新后的图景。不要重复问已解决的问题。

本技能接收当前对话上下文与代码库理解，产出一份规格说明。不要访谈用户；只需综合你已经知道的内容。

问题追踪器与分诊标签词汇本应已提供给你。如果没有，请告诉用户去运行 `/setup-matt-pocock-skills`。

## 流程

1. 探索仓库以了解代码库的当前状态（如果还没做过）。整份规格说明都要使用项目的领域词汇表，并尊重你所触及区域的任何 ADR。

2. 勾画出你将要测试该功能的"接缝（seam）"。应优先复用已有接缝，而非新建。使用尽可能高的接缝。如果需要新接缝，在你能达到的最高点提出。跨代码库的接缝越少越好——理想数量是一个。

   与用户确认这些接缝是否符合他们的预期。

3. 用下面的模板写规格说明，然后把它发布到项目问题追踪器。打上 `ready-for-agent` 分诊标签——无需额外分诊。

<spec-template>

## Problem Statement 问题陈述

从用户视角出发，用户正面临的问题。

## Solution 解决方案

从用户视角出发，该问题的解决方案。

## User Stories 用户故事

一份很长、带编号的用户故事列表。每个用户故事格式如下：

1. 作为 <角色>，我想要 <功能>，以便 <收益>

<user-story-example>
1. 作为手机银行客户，我想要查看账户的余额，以便我能对开销做出更明智的决策
</user-story-example>

这份用户故事列表应当极其详尽，覆盖该功能的所有方面。

## Implementation Decisions 实现决策

一份已做出的实现决策列表。可包含：

- 将被构建/修改的模块
- 这些模块中将被修改的接口
- 来自开发者的技术澄清
- 架构决策
- 模式（schema）变更
- API 契约
- 具体交互

**不要**包含具体文件路径或代码片段。它们可能很快过时。

例外：如果某个原型产出的代码片段比散文更精确地编码了一个决策（状态机、reducer、schema、类型形态），就把它内联到相关决策中，并简要注明它来自原型。只截取富含决策的部分，而不是一个能跑的 demo，只要重要的那几行。

## Testing Decisions 测试决策

一份已做出的测试决策列表。包含：

- 什么叫一个好测试的描述（只测外部行为，不测实现细节）
- 哪些模块将被测试
- 测试的先验做法（即代码库中类似类型的测试）

## Out of Scope 范围之外

本规格说明不涵盖之物的描述。

## Further Notes 补充说明

关于该功能的任何其它备注。

</spec-template>

# 设计两次（Design It Twice）

当用户想要为一个选定的加深候选方案探索其他接口时，使用这个并行子代理模式。基于 "Design It Twice"（Ousterhout）：你的第一个点子不太可能是最好的。

使用 [SKILL.md](SKILL.md) 中的词汇：**module 模块**、**interface 接口**、**seam 接缝**、**adapter 适配器**、**leverage 杠杆**。

## 流程

### 1. 框定问题空间

在派生子代理之前，为选定的候选方案写一段面向用户的、关于问题空间的解说：

- 任何新接口都需要满足的约束
- 它将依赖的东西，以及它们属于哪个类别（见 [DEEPENING.md](DEEPENING.md)）
- 一段粗略的示意性代码草图，用来让约束落地——不是提议，只是让约束变具体的一种方式

把这段展示给用户，然后立刻进入第 2 步。用户在阅读思考的同时，子代理在并行工作。

### 2. 派生子代理

并行派生 3 个以上子代理。每个都必须为加深后的模块产出一个**截然不同**的接口。

给每个子代理一份独立的技术简报（文件路径、耦合细节、来自 [DEEPENING.md](DEEPENING.md) 的依赖类别、接缝背后是什么）。这份简报独立于第 1 步中面向用户的问题空间解说。给每个 agent 一个不同的设计约束：

- Agent 1："最小化接口：最多瞄准 1–3 个入口点。最大化每个入口点的杠杆。"
- Agent 2："最大化灵活性：支持大量用例与扩展。"
- Agent 3："为最常被调用的那一方优化：让默认情形变得微不足道。"
- Agent 4（如适用）："围绕端口与适配器来设计跨接缝依赖。"

在简报里同时放入 [SKILL.md](SKILL.md) 的词汇与 CONTEXT.md 的词汇，让每个子代理的命名与架构语言、项目的领域语言保持一致。

每个子代理输出：

1. 接口（类型、方法、参数，外加不变量、顺序、错误模式）
2. 展示调用方如何使用它的用法示例
3. 实现在接缝背后隐藏了什么
4. 依赖策略与适配器（见 [DEEPENING.md](DEEPENING.md)）
5. 权衡：杠杆高在哪里、薄在哪里

### 3. 呈现与对比

按顺序呈现各设计，好让用户能逐个吸收，然后用散文对比它们。按**深度（depth）**（接口处的杠杆）、**局部性（locality）**（变更集中在哪里）和**接缝位置（seam placement）**来对比。

对比之后，给出你自己的推荐：你认为哪个设计最强、为什么。如果不同设计中的元素能很好地结合，提议一个混合体。要有主见：用户想要一个有力的判断，而不是一份菜单。

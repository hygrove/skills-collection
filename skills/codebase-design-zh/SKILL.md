# 代码库设计（Codebase Design）

设计**深模块**：小接口背后藏大量行为，放在干净的接缝上，能通过那个接口测试。凡是正在设计或重构代码的地方，都用这套语言和这些原则。目标是给调用方"杠杆"，给维护者"局部性"，给所有人"可测性"。

## 词汇表（Glossary）

严格使用这些词，不要拿 "component"、"service"、"API"、"boundary" 去替换。"语言一致"本身就是重点。

**Module（模块）**：任何有接口、有实现的东西。刻意做到尺度无关：一个函数、类、包，或跨层的切片。*避免*：unit、component、service。

**Interface（接口）**：调用方为了正确使用模块而必须知道的一切：类型签名，以及不变量、顺序约束、错误模式、所需配置、性能特征。*避免*：API、signature（太窄，它们只指类型层面的表面）。

**Implementation（实现）**：模块内部的东西，它的代码体。区别于 **Adapter（适配器）**：一个东西可以是"小适配器 + 大实现"（一个 Postgres 仓储），也可以是"大适配器 + 小实现"（一个内存假对象）。当话题是接缝时用 "adapter"，否则用 "implementation"。

**Depth（深度）**：接口处的杠杆。调用方（或测试）每学会一个单位的接口，就能驱动多少行为。一个模块在"小接口背后藏大量行为"时是**深**的；"接口几乎和实现一样复杂"时是**浅**的。

**Seam（接缝）** _(Michael Feathers)_：你不必在那个位置编辑就能改变行为的地方；是模块的接口所**在的位置**。接缝放哪本身是一个设计决定，与它背后放什么无关。*避免*：boundary（与 DDD 的 bounded context 重载了）。

**Adapter（适配器）**：在接缝处满足某个接口的具体东西。描述的是*角色*（它填哪个槽），不是实质（里面是什么）。

**Leverage（杠杆）**：调用方从深度中得到的。每学会一个单位的接口，就多一分能力。一份实现在 N 个调用点和 M 个测试上回本。

**Locality（局部性）**：维护者从深度中得到的。改动、bug、知识、验证都集中在一处，而不是散在调用方之间。改一次，处处修好。

## 深 vs 浅

**深模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│   小接口            │  ← 方法少、参数简单
├─────────────────────┤
│                     │
│  深实现             │  ← 复杂逻辑藏在里面
│                     │
└─────────────────────┘
```

**浅模块** = 大接口 + 极少实现（要避免）：

```
┌─────────────────────────────────┐
│       大接口                    │  ← 方法多、参数复杂
├─────────────────────────────────┤
│  薄实现                         │  ← 只是透传
└─────────────────────────────────┘
```

设计接口时问自己：

- 我能减少方法数量吗？
- 我能简化参数吗？
- 我能把更多复杂度藏起来吗？

## 原则

- **深度是接口的属性，不是实现的属性。** 一个深模块内部可以组合出小的、可 mock、可替换的部件；它们只是不在接口里。一个模块可以有**内部接缝**（私有于实现，供它自己的测试使用），也有接口处的**外部接缝**。
- **删除测试。** 想象删掉这个模块。如果复杂度消失了，它只是个透传层；如果复杂度在 N 个调用方处重新出现，那它才物尽其用。
- **接口就是测试面。** 调用方和测试跨越同一个接缝。如果你要测到接口*之外*，那模块的形态大概不对。
- **一个适配器意味着一个假设中的接缝；两个适配器意味着一个真实的接缝。** 除非真有东西在接缝两侧变化，否则别引入接缝。

## 为可测性而设计

好的接口让测试变得自然：

1. **接收依赖，而不是创建依赖。**

   ```typescript
   // 可测
   function processOrder(order, paymentGateway) {}

   // 难测
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，而不是产生副作用。**

   ```typescript
   // 可测
   function calculateDiscount(cart): Discount {}

   // 难测
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **小表面积。** 方法越少，需要的测试越少；参数越少，测试搭建越简单。

## 关系

- 一个 **Module** 恰好有一个 **Interface**（呈现给调用方和测试的表面）。
- **Depth** 是 **Module** 的属性，相对其 **Interface** 衡量。
- **Seam** 是 **Module** 的 **Interface** 所在之处。
- **Adapter** 位于 **Seam** 上，满足 **Interface**。
- **Depth** 给调用方带来 **Leverage**，给维护者带来 **Locality**。

## 被拒绝的框架

- **把深度当作"实现行数 / 接口行数"的比值**（Ousterhout）：这会奖励往实现里灌水。我们用"深度即杠杆"取而代之。
- **把 "Interface" 当作 TypeScript 的 `interface` 关键字或类的公共方法**：太窄——这里的接口包含调用方必须知道的每个事实。
- **"Boundary"**：与 DDD 的 bounded context 重载。说 **seam** 或 **interface**。

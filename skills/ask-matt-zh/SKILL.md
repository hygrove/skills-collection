# Ask Matt（问问 Matt）

你记不住每一个技能，所以来问。

**流程（flow）** 是一条穿过各技能的路线。多数路线沿着一条**主流程**走，另有两条**接入坡道**汇入其中。其余的要么独立，要么是在底层运行的词汇层。

## 主流程：想法 → 交付

大多数工作走的路线。你有一个想法，想把它构建出来。

1. **`/grill-with-docs`** 通过访谈打磨想法。只要你是**在一个工作目录里工作**，就从这里开始：它是有状态的，把学到的东西留在 `CONTEXT.md` 和 ADR 中。（没有工作目录？改用下面 Standalone 里的 `/grill-me`。两者都跑同一个 `/grilling` 原语；`grill-with-docs` 会留下纸面轨迹，所以只要有仓库可以留，它就是两者中更好的那个。）
2. **分支：你能在对话里把所有问题敲定吗？** 如果某个问题需要一个能跑的答案（状态、业务逻辑、一个你非得亲眼看不可的 UI），就绕道做个原型，用 **`/handoff`** 双向衔接（原型待在自己的目录里，而这正是 `/handoff` 的用途；见 Phase boundaries）：
   - **`/handoff`** 出去，然后针对那个文件开一个新会话，
   - **`/prototype`** 用一次性代码回答这个问题，
   - **`/handoff`** 把学到的东西带回来，并在原始想法线程里引用它。
3. **分支：这是一个多会话的构建吗？**
   - **是** → **`/to-spec`**（把线程变成一份 spec），然后 **`/to-tickets`** 把它拆成"试探子弹"工单，每个都声明自己的**阻塞边**。本地追踪器下是 `.scratch/<feature>/issues/` 里每个工单一个文件，手动按阻塞优先处理；真实追踪器下这些边变成原生的阻塞链接，所以任何阻塞已完成的工单都能被认领：对每个工单启动 **`/implement`**，在两者之间 **`/clear`** 上下文。每个工单是自包含的，所以最后一个的上下文可以随手丢弃。
   - **否** → 就在这里、同一个上下文窗口里 **`/implement`**。

   无论哪种，**`/implement`** 都通过内部驱动 **`/tdd`**（一次一个红-绿切片）来构建每个 issue，然后在提交前跑 **`/code-review`**——对 diff 的双轴审查（Standards + Spec）——收尾。当你只想在没有完整 spec 的情况下以测试先行构建某个具体行为时，单独用 **`/tdd`**；当你想针对某个固定点审查分支或 PR 时，单独用 **`/code-review`**。

### 上下文卫生

把第 1–3 步保持在**同一个不中断的上下文窗口**里（在 `/to-tickets` 之前不要压缩或清空），这样访谈、spec 和工单都建立在同一套思考之上。每个 `/implement` 再全新开始，从工单工作。

这里的限制是 **[smart zone（敏锐区）](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：模型仍能敏锐推理的窗口（前沿模型约 15 万 token）。如果会话在 `/to-tickets` 之前就接近它，不要在退化状态下硬撑；在最近的阶段边界处 `/compact` 并继续（见 Phase boundaries）。

## 接入坡道（On-ramps）

一种会产出工作、然后汇入主流程的起始情境。

- **bug 和请求堆积** → **`/triage`**。它让 issue 走过分诊角色，产出 agent 就绪的 issue，随后由 **`/implement`** 接手。

  triage 只适用于**你没创建**的 issue：bug 报告、外来功能请求、任何原始到达的东西。`/to-tickets` 产出的工单已经 agent 就绪，所以**不要对它们做 triage**。

- **有东西坏了** → **`/diagnosing-bugs`**。针对那些难啃的：第一眼就扛住的 bug、间歇性的 flakes、在两个已知良好状态之间悄悄溜进来的回归。它拒绝在拥有**紧凑反馈环**（一个已经能在这个 bug 上变红的命令）之前空谈理论，然后用回归测试修复。当真正的结论是"没有好接缝能把 bug 锁死"时，它的事后复盘会移交给 **`/improve-codebase-architecture`**。

- **庞大而迷雾重重的投入：绿地项目或巨型功能构建，大到一会话装不下** → **`/wayfinder`**，这里认知负荷最高的流程。当从这里到目的地的路还看不见时，它在 issue 追踪器上绘制一张**决策工单的共享地图**，逐个解决，产出的是**决策而非交付物**，直到迷雾退去、路清晰起来。如果说 **`/grill-with-docs`** 打磨的是你一会话能握住的 idea，wayfinder 就是给那个你握不住的 idea 用的，它更慢更密，所以只在这种时候用，绝不要用在范围清晰的功能上。

  地图清晰后，**它移交，不构建**：在主流程的 **`/to-spec`** 处汇入，它把地图里相互链接的决策坍缩成一份可构建的计划，然后照常 `/to-tickets` 和 `/implement`。把地图直接循环进 `/implement` 会跳过那次坍缩、把链接的细节丢掉，所以只有当投入结果真的很小小时，才直接去 `/implement`。

## 代码库健康

不是功能工作，只是维护。

- **`/improve-codebase-architecture`** 在你有空档时运行，让代码库保持对 agent 友好。它浮现**深化机会**；挑一个就会**生成一个想法**，可以带进主流程的 `/grill-with-docs`。它是发现候选的勘察，而下面的 **`/codebase-design`** 是你设计所选者的工作台。

## 底层词汇

两个 model-invoked 的参考，在其它技能**之下**运行，各自是其词汇的唯一真相来源。当问题是**词**而不是流程时，直接找它们；或者让上面的技能把它们拉进来。

- **`/domain-modeling`**：打磨项目的*领域*语言：挑战一个模糊的术语、消解一个被重载的词（"account" 干了三份活）、把难以逆转的决策记录为 ADR。它是 `/grill-with-docs` 驱动以保持 `CONTEXT.md` 是一份干净术语表的活跃纪律。
- **`/codebase-design`** 是深模块的词汇（module、interface、depth、seam、adapter、leverage、locality），用于设计一个模块的*形态*：在干净的接缝处、小接口背后藏大量行为。`/tdd` 和 `/improve-codebase-architecture` 都说这套语言。

## 阶段边界（Phase boundaries）

**阶段** 是会话内的一块工作：访谈、实现、QA。在两个阶段之间的**边界**上，你有五个选项，而在它们之间做选择是整个地图里最模糊的决定：

- **Continue（继续）**：原地不动。不花成本，不丢东西。
- **`/clear`**：清空窗口，当这里没什么对下一步重要时。
- **`/handoff`** 写一个可移植的 markdown 文件。范围窄：仅用于**新测试台**、**新目录**、**同事**，或在阶段中**分叉出一个侧任务**。它换来的是可移植性。
- **Subagent（子 agent）**：把一个范围严格的小任务发到它自己的窗口，拿回一份报告。
- **`/compact`** 压缩此上下文，并用它种出一个新会话。是**默认**项，位于树的底部而非最先伸手去拿。

读 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 看有序的树：五个问题、每个分支背后的推理，以及为什么"首要来源成本"让 **Continue** 成为第一个就该被排除的选项。在**边界处**做决定；阶段中则继续，或把剩下的拆给子 agent。

## 独立技能（Standalone）

完全在主流程之外。

- **`/grill-me`**：与 `/grill-with-docs` 同样无情的访谈，但**无状态**：它不在本地保存任何东西，也不构建 `CONTEXT.md`。当你**不在一个工作目录里**时（打磨一份计划、一个设计、一篇文字，任何没有仓库垫底的东西）用它。如果你在个工作目录里，改用 `/grill-with-docs`：它跑同样的访谈并留下纸面轨迹，所以严格来说更好。
- **`/grilling`** 是访谈原语本身：回合、前沿、事实是 agent 的活儿而决定是你的。`/grill-me` 和 `/grill-with-docs` 是两条具名的进入方式，而 `/triage`、`/wayfinder` 和 `/improve-codebase-architecture` 都在内部跑它。只有当你想要一个没有包装的纯访谈时，才直接用它。
- **`/resolving-merge-conflicts`** 逐 hunk 处理进行中的 merge 或 rebase 冲突，按**意图**（追溯到双方的首要来源）而非按选行来解析，然后完成操作。它绝不跑 `--abort`。独立且脱离所有流程：当你已经身处冲突中时找它。
- **`/prototype`** 是一个小的、一次性的程序，用来回答一个设计问题：这个状态模型感觉对吗，或者这个 UI 该长什么样。一次性是对代码*怎么写*的约束，不是销毁它的承诺：答案折进真实代码，而原型本身作为**首要来源**保留在从 main 分出的 `prototype/<name>` 分支上，由实现 issue 指向它。它是主流程第 2 步的绕道，但任何时候一个设计问题很难在纸面上敲定时都可以找它。
- **`/research`**：把阅读杂活委托给一个**后台 agent**：它针对**首要来源**调查一个问题，然后在仓库里留下一份带引用的 Markdown 文件。它读的时候你继续干活。它产出的文件是能带进主流程 `/grill-with-docs` 的东西，因为研究喂养的是思考而非替代它。
- **`/to-questionnaire`** 出现在挡住你的东西既不在你脑子里也不在代码库里、而在**别人**脑子里时，它给那人写一份问卷去填。它是 `/grill-me` 的反面：不是就主题访谈你，而是就**发送**（发给谁、你需要拿回什么）访谈你，并把问题对准那个缺口。拿回来的东西是给 `/grill-with-docs` 或 `/to-spec` 的材料。
- **`/wizard`** 用于只有**人类**才能做的步骤：开通基础设施、配置凭证或 CI 密钥、点完一个不熟悉的第三方仪表盘、跑一次性的迁移或切换。它生成一个交互式 bash 脚本，打开每个 URL、捕获每个值，并写进 `.env` 和 GitHub secrets，于是这套流程不再是你每次都向 agent 重新解释一遍的东西。它是 model-invoked 的，所以 agent 一旦撞上只有你能过的墙就找它。如果 agent 自己就能做，它就该自己做；这是给人类真正在回路里的时候用的。
- **`/wait-what`** 是给"没听进去的那条消息"用的 corrective。在对话中、在任何其它技能内部使用它，agent 会用你缺失的上下文、用大白话、用 `CONTEXT.md` 的词汇，重新讲一遍它刚说的话。它事后生效；`/grill-with-docs` 是前置的解药，因为早早约定好的共享语言才是阻止行话抵达的根本。
- **`/teach`**：跨多个会话学一个概念，用当前目录作为有状态的学习工作区。
- **`/writing-for-agents`** 是写"agent 消费的文档"的参考：skills、AGENTS.md、被指向的文档。

## 前置条件

**`/setup-matt-pocock-skills`**：在你的第一个工程流程之前运行，以配置其它技能所假设的 issue 追踪器、triage 标签和文档布局。自定义 issue 追踪器也可以用。

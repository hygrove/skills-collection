对 `HEAD` 与用户给定的固定点之间的 diff 做双轴审查：

- **Standards（规范）**：代码是否符合本仓库文档化的编码规范？
- **Spec（规格）**：代码是否忠实实现了来源的 issue / spec？

两个轴以**并行子 agent** 运行，互不污染对方上下文，最后由本技能汇总它们的发现。

issue 追踪器应当已经提供给你。如果 `docs/agents/issue-tracker.md` 缺失，请告诉用户去运行 `/setup-matt-pocock-skills-zh`。

## 流程

### 1. 锁定固定点

用户说的固定点是什么（commit SHA、分支名、tag、`main`、`HEAD~5` 等）。如果他们没指定，就问。

一次性记好 diff 命令：`git diff <fixed-point>...HEAD`（三点，表示与 merge-base 比较）。同时用 `git log <fixed-point>..HEAD --oneline` 记录提交列表。

继续之前，先确认固定点能解析（`git rev-parse <fixed-point>`）且 diff 非空。坏的引用或空 diff 应该在这里就失败，而不是在并行子 agent 内部才失败。

### 2. 确定 spec 来源

按以下顺序寻找来源的 spec：

1. 提交信息中的 issue 引用（`#123`、`Closes #45`、GitLab 的 `!67` 等），通过 `docs/agents/issue-tracker.md` 中的流程获取。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能匹配的 spec 文件。
4. 如果都没找到，问用户 spec 在哪。如果用户说没有，则 **Spec** 子 agent 跳过，并报告"无可用 spec"。

### 3. 确定规范来源

仓库中任何说明"代码该怎么写"的文档，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

除了仓库文档化的内容，Standards 轴始终携带下面的**坏味道基线**：一套固定的 Fowler 代码坏味道（_Refactoring_ 第 3 章），即使仓库什么都没文档化也适用。两条约束：

- **仓库优先。** 文档化的仓库规范永远胜出；当它认可基线会标记的某事物时，压制该坏味道。
- **永远是判断，不是硬违规。** 每种坏味道都是一个带标签的启发式（"可能存在 Feature Envy"），绝不是一个硬性违规。和这里的任何规范一样，工具已经强制执行的就跳过。

每种坏味道按 *是什么* → *怎么修* 对照 diff：

- **Mysterious Name（神秘命名）**：函数、变量或类型的名字看不出它做什么或装什么。→ 改名；如果想不出诚实的名字，说明设计本身模糊。
- **Duplicated Code（重复代码）**：相同的逻辑形态在改动中的多个 hunk 或文件里出现。→ 抽出共享形态，两边都调用它。
- **Feature Envy（特性依恋）**：一个方法伸进别的对象的数据比伸进自己的还多。→ 把方法移到它所依恋的数据上。
- **Data Clumps（数据泥团）**：同样的几个字段或参数总是一起出现（一个想诞生的类型）。→ 把它们打包成一个类型，传这个。
- **Primitive Obsession（基本类型偏执）**：用基本类型或字符串代替一个值得拥有自己类型的领域概念。→ 给这个概念一个自己的小类型。
- **Repeated Switches（重复开关）**：对同一类型的相同 `switch`/`if` 级联在改动中反复出现。→ 换成多态，或两边共享的一张映射表。
- **Shotgun Surgery（霰弹式修改）**：一个逻辑改动迫使 diff 中许多文件被零散编辑。→ 把一起变动的东西收进一个模块。
- **Divergent Change（发散式改动）**：一个文件或模块因为几个不相关的原因被编辑。→ 拆分，让每个模块只为一个原因变动。
- **Speculative Generality（夸夸其谈的通用性）**：为 spec 没有的需求而添加的抽象、参数或钩子。→ 删掉；内联回去，直到出现真实需求。
- **Message Chains（消息链）**：调用方不该依赖的长链 `a.b().c().d()` 导航。→ 把这段走动藏到第一个对象的一个方法背后。
- **Middle Man（中间人）**：一个类或函数基本只做转发。→ 砍掉它，直接调用真正的目标。
- **Refused Bequest（被拒绝的遗赠）**：子类或实现者忽略或覆盖了它继承的大部分内容。→ 抛弃继承，改用组合。

### 4. 并行启动两个子 agent

**Standards 子 agent 的提示**应包含：

- 完整的 diff 命令与提交列表。
- 你在第 3 步找到的规范来源文件列表，**加上第 3 步的坏味道基线原文粘贴**（子 agent 没有其他途径获取它）。
- 任务说明："按文件/hunk 报告：(a) diff 每处违反文档化规范的地方——引用规范（文件 + 规则）；(b) 你发现的任何基线坏味道——命名并引用该 hunk。区分硬性违规与判断性结论：文档化规范的违反可以是硬性的，但基线坏味道永远是判断性的，且文档化的仓库规范会覆盖基线。工具已强制执行的跳过。400 字以内。"

**Spec 子 agent 的提示**应包含：

- diff 命令与提交列表。
- spec 的路径或已获取的内容。
- 任务说明："报告：(a) spec 要求但缺失或只做了一部分的条目；(b) diff 中未被要求的行为（范围蔓延）；(c) 看起来已实现但实现有误的条目。每条发现都引用 spec 原文。400 字以内。"

如果 spec 缺失，跳过 Spec 子 agent，并在最终报告中注明。

### 5. 汇总

把两份报告放在 `## Standards` 和 `## Spec` 两个标题下，原文或略作清理。不要合并或重排发现，因为两个轴是刻意分开的（见 _为什么是双轴_）。

最后给一行总结：每个轴的总发现数，以及每个轴内最严重的问题（若有）。不要跨轴选一个总冠军——那正是分离设计要避免的重排。

## 为什么是双轴

一次改动可以过一轴而挂另一轴：

- 代码遵循每条规范，却实现了错误的东西 → **Standards 过，Spec 挂。**
- 代码完全按 issue 要求做，却破坏了项目约定 → **Spec 过，Standards 挂。**

分开报告能阻止一个轴掩盖另一个轴。

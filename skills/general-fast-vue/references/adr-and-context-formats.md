# ADR 与 CONTEXT.md 写法模板

新建 ADR 或 CONTEXT.md 时读本文件。

## CONTEXT.md 格式

### 结构

```md
# {上下文名称}

{一两句话描述这个上下文是什么、为何存在。}

## Language 语言

**Order 订单**：
{对该术语的一两句描述}
_Avoid_：Purchase、transaction

**Customer 客户**：
下单的个人或组织。
_Avoid_：Client、buyer、account
```

### 规则

- **要有主见。** 同一个概念有多个词时，挑最好的那个，把其余列在 `_Avoid_` 下。
- **定义要收紧。** 最多一两句话。定义它*是什么*，不是它做什么。
- **只收录专属于本上下文的术语。** 通用编程概念（超时、错误类型、工具模式）即便项目大量使用也不属于这里。判断标准：这是独有于此上下文的概念，还是通用编程概念？
- **当自然聚类出现时，把术语归在子标题下。** 全部术语属于一个内聚区域时，扁平列表也行。
- **CONTEXT.md 不掺杂任何实现细节。** 它是词汇表，不是规格说明、不是草稿本、不是决策存放处。

### `_Avoid_` 的写法

`_Avoid_` 是**给 AI 的负向约束**，比正向定义更有效——AI 特别容易用错同义词。

写清「为什么这两个词不同」，而不只是列出禁用词：

```md
**保留集**：
整理之后仍然留在源表目录、继续参与批处理读取的文件集合。
_Avoid_：白名单文件（白名单筛的是行，不是文件；两者不是一回事）

**key 覆盖**：
一个文件的每个数据 key，都能在保留集的其他文件里找到。它是归档的安全判据。
_Avoid_：日期窗覆盖、区间重叠（"区间重叠"只说明时间窗相交，与内容是否重复毫无关系——这正是判据设计的要点）
```

括号里的解释是**语义护栏**：它拦下的是「看起来对、实则判定错误」的推理，比单纯禁词更稳。

### 单上下文 vs 多上下文

- **单上下文（多数仓库）**：仓库根目录一个 `CONTEXT.md`。
- **多上下文**：仓库根目录一个 `CONTEXT-MAP.md`，列出各上下文、位置、彼此关系：

```md
# Context Map 上下文地图

## Contexts 上下文

- [Ordering 订单](./src/ordering/CONTEXT.md)：接收并跟踪客户订单
- [Billing 账单](./src/billing/CONTEXT.md)：生成发票并处理付款

## Relationships 关系

- **Ordering → Fulfillment**：Ordering 发出 `OrderPlaced` 事件；Fulfillment 消费它们以开始拣货
- **Ordering ↔ Billing**：`CustomerId` 与 `Money` 的共享类型
```

**惰性创建**：只在确有内容要写时才建文件。第一个术语敲定时才建 `CONTEXT.md`；需要第一份 ADR 时才建 `docs/adr/`。

## ADR 格式

### 存放与编号

`docs/adr/`，顺序编号：`0001-slug.md`、`0002-slug.md`。扫描已有最大编号加一。

### 何时写

三条**必须同时**成立：

1. **难以逆转**——日后改主意的代价是实质性的。
2. **脱离背景会令人费解**——未来的读者看着代码会纳闷「他们当初为什么这么做」。
3. **真实权衡的结果**——确实存在真正的替代方案，而你出于具体理由选了其中一个。

缺任一条就跳过。容易逆转的决策，大不了逆转回来；不令人惊讶的决策，没人会纳闷；没有替代方案的决策，除了「我们做了显而易见的那件事」之外没什么可记。

### 什么算数

- **架构形态**：monorepo？事件溯源？读模型投影？
- **上下文之间的集成模式**：领域事件还是同步 HTTP？
- **带锁定性的技术选型**：数据库、消息总线、认证提供商、部署目标。（不是每个库——只是那些换掉要花一个季度的。）
- **边界与范围决策**：「客户数据由 Customer 上下文拥有，其它上下文只按 ID 引用它。」明确的「不做」和「做」一样有价值。
- **对显而易见的路径的刻意偏离**：「我们用手写 SQL 而非 ORM，因为 X。」任何合理读者会假设相反情况的地方——这能阻止下一位工程师去「修复」某个有意为之的东西。
- **代码中不可见的约束**：合规要求、第三方契约的性能下限。
- **当拒绝并不显而易见时，记录被拒绝的替代方案**：考虑过 GraphQL 但出于微妙理由选了 REST——否则六个月后还会有人再提。

### 模板

```md
# {决策的简短标题}

{1–3 句话：背景是什么、我们决定了什么、为什么。}
```

就这些。一份 ADR 可以只有一个段落。价值在于记录*做出了*某个决策以及*为什么*，而不在于填完各个栏目。

### 可选栏目

只有当它们确实增加价值时才包含：

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：决策被重新审视时有用。
- **Considered Options**：只有当被拒绝的替代方案值得记住时。
- **Consequences**：只有当需要点出非显而易见的下游影响时。

### 篇幅参考

本项目既有的 ADR 约 40–120 行，含 `## 背景与动机` / `## Considered Options` / `## Consequences` 三段。长 ADR 的价值在于 **Consequences 段列出的「有意为之的行为」**——那是最容易被后人误改的部分。

例：某次迁移把 JSON 预物化改为 DB 直连，Consequences 里写明「时间戳语义变化（有意）：从『批处理生成 JSON 的时刻』改为『数据最后一次摄入的时刻』」。这一句防止了下一位工程师把时间戳改回去。

### Consequences 段要写「静默失效」型后果

有些后果不会报错，只会「看起来不太对」——这类最容易被后人当成设计选择放过。写 ADR 时要显式标注，并给出**验证方法**。

典型例：把第三方组件库的主题变量映射到自有令牌时，第三方自身的 `:root` 定义加载在后，同权重下会覆盖映射（页面显示组件库默认主题）。修法是双写选择器提高特异性。Consequences 里要写清：

- 症状是什么（无报错，主题色不跟随令牌）
- 根因是什么（加载顺序 + 同权重后者胜）
- 怎么验证（查产物 CSS 里该变量的定义次数与各条选择器的**特异性**——grep 的文本顺序不代表生效优先级）
- 修法是什么（`:root:root` 双写把特异性提到 (0,2,0)）

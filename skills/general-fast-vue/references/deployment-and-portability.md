# 迁移性与云端部署

> 本文讲两件**不同**的事：① 换个机器/换个用户还能跑（可移植）；② 部署到云端环境（容器化 / PaaS）。
> 它们经常被混为一谈，但**要求不同、冲突点也不同**。

## 两者的区别

| | 可移植（异地克隆） | 云端部署 |
|---|---|---|
| **目标** | 换台机器、换个用户、换个 OS 也能跑起来 | 在云平台跑起来并对外提供服务 |
| **数据在哪** | 本地文件（随项目走） | **远端**（容器本地盘 / 托管数据库 / 对象存储） |
| **状态** | 可以有状态（文件就在那儿） | **多副本时必须无状态** |
| **调度** | 本机计划任务 / cron | 平台 Cron / Cloud Scheduler / 外部调度器 |
| **端口** | 固定即可（本地用） | **必须读平台注入的 `PORT`** |
| **数据目录** | 任意本地路径 | **多数 PaaS 只读**，需挂卷或改用托管存储 |

**关键判断**：本地单机的「一切都在文件系统里」的好架构，搬到云端可能处处碰壁——**不是架构错了，是运行环境变了**。

---

## 一、可移植性：让项目「换个地方还能跑」

### 1. 路径必须从「模块位置」或「环境变量」推导

```python
# ❌ 写死：换机器/换用户就找不到
DATA_ROOT = "E:\\some-project\\ResourceData"
DATA_ROOT = "/Users/me/projects/data"

# ✅ 从模块位置推导（项目跟着代码走）
from pathlib import Path
BACKEND_DIR = Path(__file__).resolve().parent.parent
DATA_ROOT = BACKEND_DIR / "app" / "data"

# ✅ 环境变量优先，给一个默认值（本地开发零配置，部署时覆盖）
import os
DATA_ROOT = Path(os.getenv("APP_DATA_DIR", BACKEND_DIR / "app" / "data"))
```

**判断标准**：把项目文件夹复制到另一台机器、改了用户名、或者从 Windows 拷到 Linux——**不改任何代码就能跑**。

**跨 OS 的额外坑**：
- **路径分隔符**：永远用 `pathlib.Path`，不要手拼 `"/"` 或 `"\\"`。
- **大小写**：Windows 不区分大小写，Linux 区分。`ResourceData` 写成 `resourcedata` 在 Windows 能跑，在 Linux 找不到。
- **中文路径**：某些工具链对非 ASCII 路径有兼容问题（尤其打包、编译、Node 依赖解析）。**若目标环境路径可能含中文，尽量让数据目录与代码目录分离**（用环境变量指向无中文的路径）。
- **行尾符**：Windows 用 CRLF，Linux 用 LF。跑批脚本（`.sh`）在仓库里要考虑 `.gitattributes` 统一。

### 2. 依赖要能离线/可复现安装

- **锁文件必须进版本库**：`package-lock.json`、`uv.lock` / `requirements.txt`（带版本号）。
- **系统级依赖要显式声明**：容器里需要 `libavif-dev` 这类系统库时，写进 Dockerfile 而不是「我本地装过了」。
- **镜像源要考虑可达性**：默认 PyPI 在某些网络环境不可达 → 配 `PIP_INDEX_URL` 镜像源。

### 3. 数据的「种子」与「产物」要分清

| 类别 | 例子 | 处理 |
|---|---|---|
| **种子数据** | 样例 CSV、测试夹具 | 进版本库（**脱敏后**） |
| **运行时产物** | SQLite 库、图片、缩略图、`status.json` | 不进版本库，`.gitignore` + 忽略配置双保险 |
| **源数据** | 商家下载的原始 Excel | **通常不进版本库**（体积 + 敏感） |

**异地克隆的完整流程**：克隆代码 → 放一份种子数据到约定的源目录 → 跑一次批处理 → 得到完整数据库与图片。**这个流程必须写进 README**，否则别人克隆下来不知道放哪。

### 4. 可移植性闸门

```bash
python <skill>/scripts/check_portability.py <项目目录> [--allow-port 8000]
```

检查两类硬编码：**绝对路径字面量** 与 **固定端口**。`--allow-port` 声明「这个端口允许写死」（如开发期 vite 的 5173）。

> ⚠️ 判定要精确。用 `:\s*(\d{2,5})` 这种宽松模式会把「阈值 5000」「比率 : 0.5」全当端口——**误报一多，闸门就会被加豁免绕过，那才是真正的失败**。

## 二、云端部署：三类目标形态

### 形态 A · 单容器自托管（最接近本地形态）

自己带 Dockerfile，`docker run` 或编排平台跑。**状态在容器本地盘**。

**必须满足**：
- **端口读 `PORT` 环境变量**（平台注入），给默认值兜底本地开发：
  ```python
  PORT = int(os.getenv("PORT", "8000"))
  ```
- **数据目录挂卷**：`/app/data` 挂到持久卷，否则容器重建数据就没了。
- **源数据目录挂卷**（只读挂载即可）。
- **健康检查端点**：`/health` 返回 200，不依赖任何业务数据。
- **优雅退出**：收到 SIGTERM 时停止接新请求、做完手上的活再退。用 `tini` 作 PID 1 回收僵尸进程。
- **日志走 stdout/stderr**（不是文件）——平台收集容器日志。⚠️ 这与「禁裸 print」铁律不冲突：**用 `logging` 输出到 stdout 即可**，级别与堆栈都保留。

**调度**：容器内 cron，或平台 Cron 调一个 HTTP 触发端点。⚠️ **容器内 cron 的问题是：多副本会重复跑**。要么固定副本数为 1，要么把调度外置。

### 形态 B · 托管后端（把状态交给平台）

用平台的托管数据库、对象存储、认证服务。

**这会推翻一部分本技能的数据层裁决**：
- SQLite 单文件 → 托管数据库（本技能 §3.1 的裁决前提是「随项目走、零运维」，托管 DB 恰好是反面）
- 手写 SQL + 整表重算 → 仍可保留（长表 + 比率不入库的规则与存储无关）
- 事实表只增不减 → 仍适用，但「整表重算」在托管 DB 上代价更高（要考虑事务与并发）

**判断依据**：**「事实表可随时重建」这条前提是否还成立？** 若源数据每次都从文件批处理而来 → 成立；若同时有用户实时写入 → 不成立（此时分层，见 `read-write-layering.md`）。

### 形态 C · 单端口发布（把项目发成在线链接）

适合快速演示、内部工具、原型。

**平台的硬约束（必须提前知道，否则改造成本很高）**：
- **只给一个 HTTP 端口**，没有数据库/缓存/消息队列进程。
- **存储必须住在应用里**：SQLite 文件、JSON 文件、浏览器端存储都行。
- **需要外部数据库的项目（MySQL / PostgreSQL / Redis / MongoDB）不可发布**——除非连的是**公网可达的托管数据库**（平台容器能出网）。
- **端口由平台注入 `PORT`**，启动命令必须监听它。
- **不支持的运行时**：JVM / Maven / Gradle 项目（沙箱里没有这些构建链）。

**设计含义**：这类平台的天然形态就是「**单端口 + 应用内存储**」——**与本技能的架构高度契合**。这也是为什么「嵌入式单文件数据库」是这类项目的好选择。

## 三、跨形态都要满足的六条

无论部署到哪，这六条都成立：

1. **端口读环境变量**：`PORT = int(os.getenv("PORT", "8000"))`，别写死。
2. **路径从模块位置或环境变量推导**，不用绝对路径字面量。
3. **数据与代码分离**：产物目录可配置、可挂载、可丢弃重建。
4. **数据库不进版本库**，且能从源数据重建。
5. **有健康检查端点**，且不依赖业务数据。
6. **日志走 stdout/stderr**（`logging` 的 StreamHandler），不要写本地日志文件——云端收集的是标准流。

### 第 6 条的常见误区

「日志写文件」在本地没问题，在云端是**双重故障**：容器日志看不到（平台只看 stdout/stderr），且容器重建后日志文件也没了。

**正确做法**：`logging.StreamHandler(sys.stdout)` —— 级别、堆栈、结构化字段全都保留，同时被平台采集。

## 四、部署形态判定表

| 需求 | 形态 | 关键前提 |
|---|---|---|
| 内部自用、本机跑 | 不部署 | 固定端口可以 |
| 局域网共享 | 单容器自托管 | 挂卷 + `PORT` |
| 云上跑、要定时刷新 | 单容器自托管（调度外置） | 源数据挂卷只读 |
| 快速演示 / 发链接给同事 | 单端口发布 | 存储在应用内（SQLite/JSON） |
| 多用户 / 并发写入 / 结构演进 | 托管后端 | **重新裁决数据层**（见 `read-write-layering.md`） |

## 五、常见失败模式

| 症状 | 根因 | 修法 |
|---|---|---|
| 本地能跑，云端起不来 | 端口写死，平台注入的 `PORT` 被忽略 | 读 `PORT` 环境变量 |
| 容器起来了，数据没了 | 产物目录没挂卷，重建即丢 | 挂持久卷，或改用托管存储 |
| 容器启动即崩（Permission denied） | 路径写死到宿主机目录，容器里不存在 | 路径环境变量化 + 目录用 VOLUME 声明 |
| 日志里什么都没有 | 日志写进了容器内文件 | 改走 stdout/stderr |
| 定时任务重复执行 | 多副本 × 容器内 cron | 调度外置到平台 Cron，或固定单副本 |
| 跨机器跑不起来 | 绝对路径字面量 | 路径从 `__file__` 或环境变量推导 |
| Linux 上找不到文件 | 路径大小写与 Windows 不一致 | 统一大小写；用 `Path` 而非字符串拼接 |

### 实例：容器入口写死端口

一个真实项目的容器入口原本长这样：

```dockerfile
EXPOSE 8000
```
```sh
# entrypoint.sh
exec uvicorn backend.app.main:app --host 0.0.0.0 --port 8000
```

**在自托管 Docker 上完全正常**（自己映射端口即可）。但搬到 Cloud Run / K8s 就会失败：平台注入 `PORT=8080`，容器却监听 8000 → 健康检查探不到 → 流量进不来。

**修法**（一处改动，两种场景都对）：

```sh
# entrypoint.sh
exec uvicorn backend.app.main:app --host 0.0.0.0 --port "${PORT:-8000}"
```

```dockerfile
# Dockerfile
EXPOSE 8000
# ⚠️ EXPOSE 只是文档性声明，平台不读它。真正的端口协商靠 $PORT。
# 保留 8000 是为了本地 docker run 时的可读性；云端由平台注入 PORT。
```

> **关键点**：`EXPOSE` 在现代容器平台里**不决定实际端口**——它只是文档性声明。平台靠 `PORT` 环境变量协商。所以**入口命令必须读 `PORT`**，无论 `EXPOSE` 写的是什么。

## 六、闸门

```bash
python <skill>/scripts/check_portability.py <项目目录> [--allow-port 8000]
```

检查两类硬编码：**绝对路径字面量** 与 **固定端口**。

- `--allow-port` 声明「这个端口允许写死」——如开发期 vite 的 5173、本地 compose 的 8000。
- 闸门会扫 `.py/.ts/.js/.vue/.sh/.bat/.ps1/.yml/.yaml/.toml/.cfg/.ini`，自动排除 `node_modules`、`.venv`、`.scratch`、`dist` 等目录。

> ⚠️ **误报比漏报更危险**：误报一多，人就会加豁免绕过，闸门随即失效。所以判定刻意收窄——端口只认三种明确形态（`--port 8000` / `port=8000` / `host:8000`），不把「阈值 5000」「比率 : 0.5」误判成端口。

> ⚠️ **闸门只能判「形态」，判不了「语义」**：路径指向的目录是否存在、端口是否冲突、容器里该挂什么卷，它都不知道。那些要靠部署清单人工核对。

---

## 七、部署前的检查清单

- [ ] `check_portability.py` 通过（无绝对路径字面量、无意外硬编码端口）
- [ ] 端口读 `PORT` 环境变量，且有默认值兜底本地开发
- [ ] 数据目录可配置；容器里已声明为可挂载卷
- [ ] 源数据目录以**只读**方式挂载（数据源语义上只读）
- [ ] 数据库不在镜像里、不在版本库里；能从源数据重建
- [ ] 有 `/health` 端点，不依赖业务数据与源文件
- [ ] 日志走 stdout/stderr（不是本地文件）
- [ ] 定时刷新：副本数为 1，或调度外置（避免重复执行）
- [ ] 收到 SIGTERM 能优雅退出（停接新请求 + 做完在做的事）
- [ ] 种子数据已脱敏；README 写清「克隆后放哪、跑什么命令」
- [ ] 若目标是托管后端：**已重新裁决数据层**（事实表可重建的前提是否还成立）

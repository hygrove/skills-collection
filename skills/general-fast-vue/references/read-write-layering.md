# 读写分层：给数据看板加写入能力的方法

> 本文是**通用方法**，不含任何具体项目的表名或字段名。
> 判定入口见 SKILL.md 步骤 1.5；执行入口见步骤 2.5。

## 问题的本质

一个纯分析项目长这样：

```
源文件 ──批处理──▶ 事实层（只增不减）──▶ 查询层 ──▶ 图表
```

它跑得好好的，因为**只有一条变更来源**——源文件。所有数据都是「派生出来的」，所以随时可以重建。

现在要加写入能力（运营改一条错数据），于是有了**第二条变更来源**——人。

**两条来源的生命周期、语义、可靠性都不同**，这就是问题的本质。不是「怎么加个 UPDATE 接口」，而是「怎么让两种来源共存而不互相破坏」。

## 三条会被打破的假设

| 原假设 | 加写入后 | 破坏后果 |
|---|---|---|
| 事实层 = 源文件的投影，可随时重建 | 事实层里有人改过的值 | 重建 = 冲掉用户的修改（静默丢数据） |
| 事实层结构不需要演进 | 修正要记「谁改的、为什么」 | 加字段无序，逐渐失控 |
| 聚合口径唯一 | 有人改了一个分子 | 比率口径漂移，跨期汇总对不上 |

## 三层模型

```
┌─────────────────────────────────────────────┐
│  业务层（主数据）                              │
│  组织 / 商品 / 阈值配置 / 用户                 │
│  变更来源：用户 CRUD                            │
│  规则：可增删改 + 需要迁移机制                  │
└─────────────────────────────────────────────┘
┌─────────────────────────────────────────────┐
│  修正层（人工覆盖）                            │
│  (业务键, 字段, 值, 原因, 操作人, 版本, 时间)  │
│  变更来源：用户操作                            │
│  规则：按键+字段存；查询时叠加；可撤销          │
└─────────────────────────────────────────────┘
┌─────────────────────────────────────────────┐
│  事实层（源文件投影）                          │
│  只增的原始列（数量/金额/次数）                │
│  变更来源：摄入流程                            │
│  规则：只增不减；比率不入库；用户不直接改        │
└─────────────────────────────────────────────┘
```

**层的划分依据是「变更来源」，不是「表长什么样」。** 一个用户建的、字段很少的表，若它的值永远由用户决定，它就属于业务层；一个字段很多的表，若它永远由摄入流程决定，它就属于事实层。

## 修正层的设计要点

### 键的选择

修正层的主键 = **(业务键, 字段名)**。

业务键是「哪一行」——由事实层的粒度决定（通常是 `日期 + 组织 + 商品` 这类维度组合）。
加上字段名，才能表达「只改这一个指标」。

**为什么不用整行覆盖**：整行存意味着每次修改都要先读出当前全部字段、覆盖写回——而「当前值」可能已经被另一条修正改过，读取与写入之间的窗口期会产生覆盖丢失。按字段存则天然规避：每个字段独立，互不影响。

### 生效时机：查询时叠加

```
事实值    SELECT amount FROM 事实层 WHERE 键 = ?
修正值    SELECT value FROM 修正层 WHERE 键 = ? AND field = 'amount'
最终值    COALESCE(修正值, 事实值)
```

**为什么不在跑批时合并**：合并意味着把修正写回事实层——那会同时破坏「只增不减」和「可随时重建」，并且下一次跑批还要再合并一次（否则修正丢失）。查询时叠加是唯一让两层都保持本性的做法。

**代价**：每次查询多一次查找。数据量大时可优化为「一次性载入修正表到内存再合并」——但**合并逻辑必须与查询路径共用同一个函数**，否则会出现两处口径不一致。

### 接入点

在**数据源协议的实现处**叠加，而不是在每个查询里改。

理由：下游的指标派生、聚合、格式化、图表全部自动生效。新增查询不会忘记叠加——因为它们都走同一个数据源。

**判据**：找到「所有读取都从这里进」的那个函数。若找不到这样的收敛点，说明数据访问路径是散的，此时叠加成本会很高——先做访问路径收敛，再谈修正。

### 审计字段

| 字段 | 作用 | 现在就要吗 |
|---|---|---|
| 修正人 | 谁改的 | ✅ 必须 |
| 原因 | 为什么改 | ✅ 必须（运营事后追责/复盘） |
| 时间戳 | 什么时候 | ✅ 必须 |
| 版本号 | 第几版 | ⚠️ **建议现在加**——将来多人协作时它是乐观锁的基础，现在加只是一列成本 |

### 撤销

修正层的行被删除 → 查询自然回落到事实层原值。**撤销不需要额外机制**，这是修正层相对「直接改事实层」的一个隐性优势。

## 不该开放修正的字段

带**跨行合并语义**的列。

典型例子：某列的值是「同组内最后一行非空值」或「同组内首行值」——这是从多行归约出一个值的规则。此时：
- 修正第 5 行的这个列 → 合并后整组的显示都变了
- 用户以为只改了一行，实际影响一整组

**判据**：这个列的值在读取时是否依赖其他行？依赖 → 不开放修正。
**做法**：修正层只开放**数值指标列**（它们逐行独立）。

## 业务层与事实层的关系

业务层（主数据）的变更**不应触达事实层**。两者通过关联连接，不是通过复制。

```
事实层行 (org_id, item_id, ...)  ──关联──▶  业务层实体 (组织名, 商品标题, ...)
```

主数据改了（比如组织改名），事实层不需要动——展示时关联当前主数据即可。
⚠️ 如果业务层的数据被**复制**进事实层，就会产生双真相：改了一处，另一处还是旧值。这是与「比率不入库」同源的错误，只是发生在不同层。

## 需要 ORM 与迁移的部分

只有业务层需要。事实层的「每次重建」机制让迁移脚本失去意义。

| 层 | 结构演进方式 |
|---|---|
| 事实层 | 改建表语句 + 重跑摄入（重建即可） |
| 修正层 | 加列即可（结构简单，且很少变） |
| 业务层 | **需要迁移机制**（表会长期存在，结构持续演进） |

## 闸门怎么适配

事实层只增不减的闸门按**表角色**判定：

- 自动识别：表名含宽表/明细/日级/流水特征词
- 显式声明：`--fact-table 表名` 声明事实表，`--exempt-table 表名` 豁免可写表

**合法的删除不违规**：整表重算（无 WHERE）、按键重算（DELETE 后写回）、保留策略淘汰过期快照、辅助表随源文件清理、测试夹具造数据。

**违规的语义** = 「事实层被当成了可写业务表」。

## 什么时候必须停下来重新裁决

| 触发条件 | 为什么本方法不够用 |
|---|---|
| 多人同时编辑同一条记录 | 需要乐观锁与冲突检测；「最后写入者获胜」会静默丢数据 |
| 事实层不再整表重算（改增量更新） | 只增不减的适用面要重新界定 |
| 修正需要审批流 | 修正层要加状态机；查询只叠加「已生效」的修正 |
| 外部用户写入（非内部运营） | 需要认证、权限、审计；性质从内部工具变成业务系统 |

这四种情况都应当**写 ADR**，而不是照搬本方法。

## 两个必须提前裁决的缺口

修正层模型有两个真实的缺口，**上手前必须想清楚**，否则会出现「静默的错值」。

### 缺口 1 · 源侧后来被正确化，与修正层打架

**场景**：巡检员上传的记录错了 → 店长改了分（修正层覆盖）→ 后来巡检员/主管在源文件里把那条记录**改对了** → 跑批刷新了事实层 → **修正层的旧覆盖仍压住真实值**，且无任何报错。

**根因**：修正层只记录了「改成什么」，没记录「针对哪一版事实值」。事实值变了，修正就过期了。

**两种解法**：

| 解法 | 做法 | 适用 |
|---|---|---|
| **修正携带事实值指纹** | 修正行存一份被修正时的原值；查询时若事实值已变，修正标记为「待复核」而非直接生效 | 需要人工确认的场景 |
| **事实值变更即作废修正** | 事实层该键的值变化时，删除或标记对应修正 | 事实值变更是「修正目的达成」的场景 |

**判据**：问一句「事实层这个值变了，说明什么？」——是「数据被订正了」（→ 作废修正），还是「数据被重新采集了」（→ 修正仍适用）。**判不出来就要走复核流程。**

### 缺口 2 · 「新增一行」不属于任何一层

**场景**：店长想补录一条当天漏传的巡检。这**不是**对事实的覆盖，是**新事实**。

它落不进事实层（「用户不直接改」），也落不进修正层（修正层是「键 + 字段」的覆盖，键不存在就无处可放），业务层装它也不对（它不是主数据）。

**三种处理**：

| 方案 | 做法 | 代价 |
|---|---|---|
| **补录也走源侧** | 用户补录 → 写入源文件/上传接口 → 跑批摄入 | 补录不是即时可见；要等跑批 |
| **修正层支持「新增行」** | 修正层允许键不存在于事实层，语义是「此键应有此值」 | 修正层语义变复杂；查询要处理「只有修正没有事实」的行 |
| **独立的补录层** | 第三张表，查询时与事实层 UNION | 层次增加；口径要明确优先级 |

**建议**：优先「补录也走源侧」——它不破坏任何层的语义，代价只是即时性。若业务要求即时可见，用「修正层支持新增行」，但要在 ADR 里写清「只有修正没有事实」的行如何参与聚合（分母算不算它？）。

## 验收清单

写完修正层后逐条核对：

- [ ] 修正写入后，查询结果立即变化（不需要等跑批）
- [ ] 跑批之后，修正确然还在（没有被冲掉）
- [ ] **事实层该键的值变化后，修正层的处置已明确**（作废 / 标记待复核 / 仍适用——见缺口 1）
- [ ] **「补录新行」的路径已明确**（走源侧 / 修正层支持 / 独立层——见缺口 2）
- [ ] 撤销修正后，值回到事实层原值
- [ ] 聚合口径与修正前一致（同一组数据，对比聚合结果）
- [ ] **聚合口径的对照方式正确**：修正的目的就是让某些聚合值变化，所以对照不是「聚合结果不变」，
      而是「**未被修正的项聚合结果不变**，被修正的项按修正值变化，且**所有比率按新分子新分母重算**」
- [ ] 修正层有审计字段（人、原因、时间）
- [ ] 跨行合并语义的列没有开放修正
- [ ] 事实层没有出现逐行 DELETE/UPDATE（闸门通过）
- [ ] 修正层的写入路径是 UPSERT，不是「先删后插」（否则并发下会丢修正）

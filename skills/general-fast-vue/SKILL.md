# FastAPI + Vue3 单端口全栈项目架构

## 这个技能解决什么

这类项目的共同形状：**一个后端进程、一个端口**，同时提供业务接口、构建后的前端页面、静态资源与数据；数据侧常从多份 Excel/CSV/接口批处理成一张可查询的指标库。

**本技能提供的是「已踩过的坑」，不是通用教程。** 下面 8 条铁律里，第 1 条（挂载顺序）与第 3 条（事实表只增不减）对应手册标 🔴 的两处致命项（§2.1、§3.4）；第 4 条（logging）是本技能新增的可观测性下限（手册未收录）。

> ⚠️ 手册中标 🔴 的只有 **2 条约束**（§2.1、§3.4）。本技能的铁律表是**扩展集合**，不是手册 🔴 的镜像——不要把两者当成同一份清单。
>
> ⚠️ 本技能的**适用范围是「数据进得来、看得懂」的项目**（指标库、看板、分析工具、内部工作台）。若你的项目是纯 CRUD 后台（用户输入为主、无批处理数据源），跳过步骤 2 与步骤 2.5，直接从步骤 3 开始——那类项目不需要事实层，也不需要本技能的数据管道裁决。

## 先判定：项目属于哪种数据形态

**这一步决定后续所有铁律怎么适用。** 判错形态 = 整套规则套错地方。

| 形态 | 判定特征 | 铁律 3（只增不减） |
|---|---|---|
| **纯分析**（只读看板） | 数据来自文件批处理；用户只看不改 | 全面适用 |
| **分析 + 人工修正** | 运营会发现某条数据错了，要能在线改掉 | 适用，但只作用于**事实层**；修正走**修正层** |
| **分析 + 外部提交** | 用户在自己那边产生原始数据（拍照上传、填报表单），系统只是收 | 适用；**但外部提交必须落在源侧**（写入源文件/上传接口），不能直接写事实层——否则事实层变成可写表，铁律 3 立刻破 |
| **分析 + 业务实体 CRUD** | 组织/商品/供应商等主数据要增删改查 | 只适用于**事实层**；业务层另立规则 |
| **实时协作** | 多人在页面上同时改，要实时看到他人改动 | 事实层不适用；需乐观锁与冲突检测 |

> ⚠️ **不要把「用户改了一条数据」当成「事实表可以随便改」。** 两者的区别是后面整节的内容。
>
> ⚠️ **「用户产生原始数据」与「用户修正已有数据」是两种不同的写入**——前者是**新事实**（该进源侧，走摄入流程），后者是**覆盖**（该进修正层）。混为一谈会让事实层的写入来源变得不可控。

## 铁律（违反即返工）

以下八条是硬约束。每条都配一个机器闸门，闸门不通过就是改错了。

| # | 铁律 | 闸门 |
|---|---|---|
| 1 | **静态挂载写在业务路由与 SPA 回退路由之前**（正确顺序：静态挂载 → 业务路由 → SPA 回退） | `scripts/check_mount_order.py <backend/app> --mode spa` |
| 2 | **事实表只存可累加原始列，比率不入库** | `scripts/check_ratio_columns.py <backend>` |
| 3 | **事实表只增不减**（移走源表不删行，防僵尸行） | `scripts/check_append_only.py <backend>` |
| 4 | **后端应用代码用 logging，不用裸 print** | `scripts/check_no_bare_print.py <backend>` |
| 5 | **前端只用令牌，不写魔法值；组件库走收敛层** | `verify:tokens` + `verify:ep`（**前端项目内**，本技能不提供这两个脚本） |
| 6 | **不可逆搬移默认 dry-run，且走「指纹→断言→执行→后置核对」** | 无（人工执行清单，见下） |
| 7 | **判定与渲染分离：口径在纯函数里，有单测** | 无（单测断言，见下） |
| 8 | **前后端类型对齐：字段变更两处同改** | `vue-tsc` / `tsc` 构建即查 |

**铁律 1 的症状**：页面能开，图片全 404。浏览器拿到 200 + HTML，所以不报错——最隐蔽的一类。
**铁律 1 的实际判定比表述更严**：即使项目还没写 SPA 回退路由，只要已有业务路由，闸门也会要求 mount 写在业务路由**之前**——因为 mount 是事后追加的，等将来加回退路由时就会踩坑。**mount 要写在应用装配区（文件最前面的静态挂载段），不是「只要在回退路由之前就行」。**

**铁律 2 的症状**：单日数据对、汇总数据错。两天各 10%、20%，区间真实是 15%，比率入库后取平均只是**恰好**巧合对。

**铁律 3 的症状**：移走源表后，对应行冻结成僵尸行——仍在聚合、永不更新、零报错。**这是手册标 🔴 的头号致命项。**
**铁律 3 的判定边界**：只拦「事实表被当成可写业务表」。合法的删除不违规——整表重算（DELETE 无 WHERE）、按键重算（DELETE 后 INSERT OR REPLACE 写回）、保留策略淘汰过期快照、辅助表随源文件清理。判定靠**表角色**，不是靠「项目里有没有 DELETE」。

**铁律 4 的症状**：项目以无控制台方式启动时（Windows `pythonw.exe` + `CREATE_NO_WINDOW`），`sys.stdout` 为 None，`print()` **静默丢弃**——后端诊断信息一行都落不了盘。

**铁律 4 的理由不止这一条**（换环境时别拿「托盘模式」当理由说服人，那条论证不适用于 Linux/容器部署）：
- **无级别**——无法只筛 ERROR
- **无堆栈**——`print(str(e))` 只剩一行文字，定位不到代码行
- **无结构化字段**——无法 grep 解析、无法关联一次请求的多层调用
- **可能静默丢失**——无控制台环境下直接蒸发

### 闸门怎么跑

```bash
# 五个后端闸门（可独立跑，也可串成一条流水线）
python <skill>/scripts/check_mount_order.py    <项目>/backend/app --mode spa
python <skill>/scripts/check_ratio_columns.py  <项目>/backend
python <skill>/scripts/check_append_only.py    <项目>/backend
python <skill>/scripts/check_no_bare_print.py  <项目>/backend
python <skill>/scripts/check_portability.py    <项目>            # 迁移性 / 云端部署
```

五个脚本都以退出码表达结果：**0 = 通过，1 = 违规**。接入 CI 或推送前钩子时直接用退出码判断。

**`--mode` 参数**（`check_mount_order.py` 专用）：

| 模式 | 适用 | 判定 |
|---|---|---|
| `spa` | 后端同源托管前端产物（静态站 + SPA + 图片） | mount 必须早于业务路由与 SPA 回退路由 |
| `api` | 纯后端 API（前端独立 dev server / 独立部署） | 无回退路由 = 无此风险，直接通过 |
| `auto` | 默认。按文件内是否存在 catch-all 回退路由自动判定 | 有则按 spa，无则按 api |

**表角色参数**（`check_append_only.py` 专用）：

| 参数 | 用途 |
|---|---|
| `--fact-table 表名` | 显式声明哪些是事实表。**优先于**特征词自动识别 |
| `--exempt-table 表名` | 显式豁免某表——它像事实表但允许逐行删改（如可写的业务表） |

**端口白名单参数**（`check_portability.py` 专用）：

| 参数 | 用途 |
|---|---|
| `--allow-port 端口` | 声明「这个端口允许写死」。如开发期 vite 的 5173 |

> 表角色与端口识别都有启发式成分，**判错的后果是误报或漏报**。真实项目跑一次，若误报就用参数显式豁免并写下理由。
>
> ⚠️ **误报比漏报更危险**：误报一多，人就会加豁免绕过，闸门随即失效。所以这两个脚本的判定都刻意收窄（如端口只认 `--port 8000` / `port=8000` / `host:8000` 三种明确形态，不把「阈值 5000」误判成端口）。

**豁免范围**（脚本内已内置，不要在业务代码里绕过）：`verify_*` / `check_*` / `setup_*` / `test_*` 与 `tests/` / `scripts/` 下的 CLI 工具与测试——它们的 `print` 是给人看的正常输出、它们的删改是造夹具数据，都不是业务行为。

### 闸门能查什么、不能查什么

闸门是**文本与结构层面**的检查，不是语义证明。它们拦住的是「最容易犯、且后果最隐蔽」的那一类错误。

**能拦住的**：挂载写在业务路由之后（含 `app.mount(变量)` 与 `app.mount(函数())` 等非字面量形式——它们同样参与顺序判定）；事实表建表语句里的比率列名；事实表被逐行 DELETE/UPDATE；应用代码里的裸 `print` / `sys.stdout.write`；**绝对路径字面量与固定端口**；前端直写 `el-*` 标签或直引 `--el-*` 变量。

**拦不住的（必须靠别的手段补）**：
- DDL 写在 `.sql` 文件里（脚本只扫 `*.py`）——**故事实表的建表语句必须留在 `.py` 里**
- **手写 DDL 用变量拼表名**（`f"CREATE TABLE {TABLE} (...)"`）或省略末尾分号——同样扫不到。建表语句须写成**字面量** `CREATE TABLE 表名 (...)` 且**带分号**
- 用 ORM 模型定义表结构（DDL 由元数据生成，脚本看不见）
- 用 `ALTER TABLE ADD COLUMN` 追加的比率列
- 列名刻意取一个不含比率词根的名字（`conv` / `cr`）——**靠命名约定，闸门管不了语义**
- 挂载路径来自运行时计算的值（顺序仍会判定，但路径内容不可知）
- **比率列的 `_ratio_` 豁免机制**：列名带 `_ratio_` 标记**且**所在表不是事实表时才豁免。⚠️ 这是给「派生指标表」留的口子；事实表里加这个标记**不会**被放行（两个条件缺一即违规）。但它挡不住「事实表改名成非事实表名 + 列名带标记」这种刻意绕过——闸门不替人判断语义。
- **表角色识别错**：特征词是启发式，闸门不知道某张表在业务上到底算不算事实表——**这需要人裁决**（用参数显式声明）
- **路径/端口的语义正确性**：闸门只认「字面量形态」，路径指向的目录是否存在、端口是否冲突，它不管
- 口径算错但代码看起来对（**只有单测能抓**）

**结论**：闸门通过 = 过了最低限度，**不等于合规**。它替代不了单测，也替代不了真浏览器实测（步骤 6）。

### 闸门的技术前提（换栈时要重写）

本技能提供的五个闸门是 **Python + FastAPI + SQLite** 专属的。它们**不能**直接用于其他技术栈：

| 闸门 | 依赖的技术假设 | 换栈时的替代 |
|---|---|---|
| `check_mount_order.py` | FastAPI 的 `app.mount(...)` 与 catch-all 路由 `{path:path}` | 其他框架的等价机制（Express 的 `app.use`、Go 的 `http.Handle`、Django 的 urlpatterns 顺序） |
| `check_ratio_columns.py` | SQL 写在 `.py` 的字符串字面量里 | 其他语言同样成立；但若 DDL 在 `.sql` 文件里则需另写扫描器 |
| `check_append_only.py` | 同上 + 表名特征词识别 | 换栈时规则不变，但**特征词需按目标项目语言重写** |
| `check_no_bare_print.py` | Python 的 `print` / `sys.stdout` | 其他语言的对应输出函数 |
| `check_portability.py` | 语言无关（扫文本字面量），但文件类型白名单是 Python/JS 生态 | 换栈时规则不变，扩展文件类型即可 |

**换栈时优先移植「规则」而非「脚本」**：五条规则背后的判据（挂载顺序、比率不入库、只增不减、无裸输出、无硬编码路径与端口）是语言无关的，脚本只是它们在 Python 上的一个实现。

**中文表名与列名已支持**：事实表特征词与比率词根都含中文项（明细/流水/记录/率/占比/均值等）。若项目用其他语言（如表名是拼音），用 `--fact-table` 显式声明兜底。

## 搭建新项目的步骤

按顺序执行。每步都有完成标准，完成标准不满足就停在那步，不要往下走。

### 步骤 1 · 定边界与心智模型

确认四件事：数据源是什么（Excel / CSV / 接口 / 已有库）、指标口径是什么、谁看（内部 / 对外）、数据量级。

落成一份 `CONTEXT.md`——**只写词汇表，不写实现细节**。每个领域术语一条定义 + 一行 `_Avoid_`（列出容易被混用的同义词）。

> `_Avoid_` 是给 AI 的负向约束，效果好于正向定义——AI 特别容易用错同义词。

**完成标准**：`CONTEXT.md` 存在，且每个术语都有 `_Avoid_` 行。

### 步骤 1.5 · 判定数据形态，选定写入策略

**先问一句：这个项目将来要不要「用户能改数据」？** 这决定后续所有分层。

| 需求 | 写入策略 | 见 |
|---|---|---|
| 只看不改 | 无写入层 | 步骤 2 即可 |
| **人工修正**（运营改某条错数据） | **修正层叠加** | 步骤 2.5 |
| 业务实体 CRUD（组织/商品等主数据） | 业务层独立 | 步骤 2.5 |
| 多人实时协作 | 业务层 + 乐观锁 | 需重新裁决（见下） |

> ⚠️ **不要跳过这一步直接动手写 UPDATE。** 「给事实表加个 UPDATE 接口」看起来是最小改动，实际会同时破坏铁律 2（比率口径）与铁律 3（只增不减），并且引入「跑批把用户修改冲掉」这类静默丢数据。

### 步骤 2 · 数据层：长表 + 手写 SQL

事实表只存可累加原始列（数量、金额、次数、费用）。比率一律查询时派生：先按维度求和，再相除；分母为 0 或缺失时返回空（前端显示占位符）。

**不用 ORM。** 理由是结构性的：ORM 会诱导把派生值写进表，而那正是铁律 2 要防的。事实表是「每次跑批整表重算」，迁移脚本解决的「线上库不能停机改结构」在这里不存在。

> **例外**：SQLModel 的 **Pydantic 模型**仍可用来定义 API 请求/响应 schema（校验 + 序列化一处定义），只是**不碰 DB 映射**（不写 `table=True`）。

**如果用了 `fullstack-vf` 脚手架，先做这份清理**（脚手架默认带 ORM，与本步骤冲突）：

| 删除 | 位置 | 原因 |
|---|---|---|
| `backend/alembic/` 目录 + `backend/alembic.ini` | 脚手架生成 | 迁移机制与「整表重算」冲突 |
| `alembic`、`psycopg[binary]` 依赖 | `backend/pyproject.toml` | 本类项目用 SQLite 单文件，不需要 Postgres 驱动 |
| `class Item(SQLModel, table=True)` | `backend/app/models.py` | 表映射层不用；Pydantic schema 可保留 |
| `backend/app/routers/items.py`（整个文件） | 脚手架生成 | 它 `from ..models import Item` 并用 `session.exec(select(Item))`——删了表模型却留这个 router，后端直接 ImportError（真导入会失败） |
| `create_db_and_tables()` 及其 lifespan 调用 | `backend/app/database.py`、`backend/app/main.py` | 「启动即建表」与「跑批建表」并存会双真相 |

⚠️ **清理的连带影响**：闸门 `check_ratio_columns.py` **只扫 `*.py` 里的 `CREATE TABLE` 文本**。若保留 ORM 模型，DDL 由 ORM 元数据生成，闸门**完全看不见**——它会输出 PASS 而实际失明。故事实表的建表语句必须**手写并留在 `.py` 文件里**（如 `backend/app/db_schema.py`），这是闸门能工作的前提。

摄入用**内容哈希门控** + **幂等 upsert**：
- 已处理文件清单表存「相对路径 + 内容 sha256」；本轮哈希相同且库非空 → 跳过整段摄入；任一文件变了 → 重算整张干净事实表再幂等 upsert。
- 门控比对**全量内容哈希**，不含修改时间/大小——增、删、改名、改内容一律整表重算。

**事实表只增不减**（防僵尸行，铁律 3）：把源表移走不会清理对应行，会冻结成僵尸行——仍在聚合、永不更新、零报错。任何涉及「移走源表」的功能，必须先证明被移走的每个键在别处仍有来源。

**完成标准**：`check_ratio_columns.py` 通过；摄入可重复执行且结果一致（跑两次，库内容相同）。

### 步骤 2.5 · 读写分层：加写入能力时的分层裁决

> **何时读这一节**：步骤 1.5 判定为「需要写入」时才读。纯只读项目跳过。
> **详细方法见 `references/read-write-layering.md`**（三层模型、修正层字段设计、接入点判据、验收清单）。本节只给决策骨架。

#### 三层模型（按「变更来源」分层，不按表长什么样）

| 层 | 装什么 | 变更来源 | 规则 |
|---|---|---|---|
| **事实层** | 从源文件批处理来的指标明细 | 摄入流程 | 只增不减；比率不入库；用户不直接改 |
| **修正层** | 人对事实层的局部覆盖 | 用户操作 | 按「键 + 字段」存；查询时叠加；可撤销 |
| **业务层** | 主数据实体（组织、商品、阈值配置…） | 用户操作 | 可增删改；需要迁移机制 |

**为什么必须分层**：三类数据的变更来源与语义不同。混在一张表里，就会出现「跑批把用户改的冲掉」或「用户改坏了聚合口径」这类静默故障——且都不报错。

#### 三个必须定下的岔路

| 岔路 | 建议 | 理由 |
|---|---|---|
| **修正粒度**：按字段 / 按整行 | **按字段** | 未修正的字段自然回落到底层值；不需要「先读全行再写回」，也就没有覆盖丢失的窗口期 |
| **生效时机**：查询时叠加 / 跑批时合并 | **查询时叠加** | 跑批合并要把修正写回事实层，那会破坏只增不减，且下次跑批会再冲掉一次 |
| **存哪**：独立修正表 / 写回事实表 | **独立修正表** | 事实层保持只增不减；修正可单独审计与撤销 |

#### 接入点

在**数据源协议的实现处**叠加（读长表的那一层），不要在每个查询里改。这样指标派生、聚合、格式化全部自动生效，**比率口径零改动**——铁律 2 得以保持。

> 判据：找到「所有读取都从这里进」的那个函数。若找不到这样的收敛点，说明数据访问路径是散的——先做访问路径收敛，再谈修正。

#### 两条硬约束

- **修正层必须能撤销**：删掉修正层的行，查询自然回落到事实层原值。这是修正层相对「直接改事实层」的隐性优势。
- **带跨行合并语义的列不开放修正**：若某列的读取依赖其他行（如同组取最后一行非空值），修正它会影响整组显示。**只开放数值指标列。**

#### 两个必须提前裁决的缺口

修正层模型有两个真实缺口，**上手前必须想清楚**（详见 `references/read-write-layering.md`）：

| 缺口 | 场景 | 必须回答的问题 |
|---|---|---|
| **源侧后来被正确化** | 人工修正了 → 后来源文件里那条数据被改对了 → 跑批刷新后，**旧修正仍压住真实值**，零报错 | 事实层该键的值变了，说明「数据被订正」还是「重新采集」？前者作废修正，后者修正仍适用。判不出就走复核 |
| **新增一行不属于任何层** | 用户要补录一条当天漏传的数据——这不是覆盖，是新事实 | 补录走源侧（不破坏任何层语义，但要等跑批）、修正层支持「键不存在于事实层」（即时但语义复杂）、还是独立补录层？ |

#### 什么时候必须停下来写 ADR

- 多人同时编辑同一条记录 → 要乐观锁与冲突检测（「最后写入者获胜」会静默丢数据）
- 事实层不再整表重算（改增量更新）→ 只增不减的适用面要重新界定
- 修正需要审批流 → 修正层加状态机，查询只叠加「已生效」的修正
- 外部用户写入（非内部运营）→ 需要认证、权限、审计，性质从内部工具变成业务系统
- **事实层的粒度与摄入模型需要裁决**（例如「某店某天的总分」是检查项之和还是独立录入的原子事实）→ 粒度定错，修正层怎么设计都错

**完成标准**（需要写入的项目）：`check_append_only.py` 通过（业务表已用 `--exempt-table` 显式豁免）；修正有审计字段且可撤销；上面两个缺口都有明确处置；**聚合对照方式正确**——修正的目的就是让某些聚合值变化，所以对照不是「聚合结果不变」，而是「**未被修正的项不变，被修正的项按修正值变化，且所有比率按新分子新分母重算**」。

### 步骤 3 · 后端：单端口托管一切

一个进程、一个端口，同时提供业务接口、构建后的前端静态资源、原图与缩略图。其余路径回退到 SPA 入口页。

- **挂载顺序是硬约束**：所有 `app.mount(...)` 写在 SPA 回退路由之前（铁律 1）。
- **入口 HTML 强制 `no-store`**：`/assets` 下的文件带内容 hash，可以长缓存；`index.html` 文件名固定，缓存它会导致「改了前端却看不到变化」——极难自查。
- **数据源协议解耦**：定义统一的「数据源」接口（名字 + `取数() → 标准长表`）。接入新源 = 写一个取数函数，ETL 主流程零改动。**读与写分开实现**，别混在一个类里。
- **后端直查数据库，无中间 JSON**：API 每次请求直接查事实表。中间 JSON 会造成双真相、缓存失效、「刷新了但页面没变」。
- **所有分组/去重带「保持顺序」参数**：某些引擎默认行序随线程漂移，会导致图表重排。

**完成标准**：`check_mount_order.py` 通过；后端真导入 + 真启动成功（语法检查查不出引用错误）。

### 步骤 4 · 前端：令牌 + 判定分离 + 收敛层

- **设计令牌是唯一事实来源**：颜色、字号、圆角全部走 CSS 变量；字号写成 `calc(Npx * var(--font-scale))`，改一个系数即全站缩放。运行时把系数写入变量并持久化，首屏在框架挂载前读回防闪烁。
- **判定与渲染分离**：口径、阈值、格式化、占位符集中在纯函数模块（不碰网络、不碰 DOM），视图只渲染。判定用的格式化函数自己写——通用 formatter 的空值语义不同（空值该显示 `--` 而非 `0.00`）。服务端与前端展示文案用**同名同义常量**，两边各一条断言锁住防漂移。
- **状态分三层**：业务数据 / 瞬时 UI（路由级遮罩）/ 用户偏好（本地存储）。三者混用会互相污染。
- **装配顺序**：状态库 → 路由 → 挂载。状态库必须在路由之前（路由守卫要点亮加载态）。状态库调用放在导航运行时，不放模块顶层。
- **配置驱动**：新增模块 = 后端加一条模块规格 + 前端加一份配置，**不写新页面**。模块页是通用骨架，重复造页面 = 重复 bug。
- **数据源协议解耦**：新增数据源不触动聚合与展示链路。
- **大数据量列表**：接口强制分页 + 滚动到底拉下一页；图表只用聚合结果，不画原始点。

**组件库走收敛层**：用 Element Plus 或同类组件库时，业务组件不直接写 `el-*`，一律经 `components/ui/` 的语义包装组件；同时在 `style.css` 建立 `--el-*` → 本项目令牌的单向映射，并让 EP 的字号变量写成 `calc(Npx * var(--font-scale))`。

> 为什么：放任组件库用默认值 = 页面存在两套颜色源（改一处漏九处），且用户调字号时组件库控件不变、页面半大半小。

⚠️ **映射层必须用 `:root:root` 双写选择器**——这是个真实踩过的坑：

组件库自己的 `base.css` 也在 `:root` 上定义同名主题变量，且按需引入时**加载在项目 `style.css` 之后**。同权重（0,1,0）时**后加载者胜**，于是组件库的默认主色（EP 蓝 `#409eff`）会**整层覆盖掉你的映射**——页面看着还是组件库的原生蓝色，而你的令牌改动完全没生效。

```css
/* ✅ 双写提高特异性到 (0,2,0)，无论加载顺序都稳定压过组件库的 :root */
:root:root {
  --el-color-primary: var(--color-brand);
}
```

**验证方法**（别信肉眼）：构建后在产物 CSS 里查 `--el-color-primary` 出现了几次、**各条的选择器特异性**。grep 的**文本顺序不代表生效优先级**——决定优先级的是特异性。

> 这个坑的特征是「静默失效」：没有报错，主色看起来「不太对」但很容易被当成设计选择放过。**任何「映射层 + 第三方主题变量」的组合都要验这一条。**

**完成标准**：令牌校验 + 组件库规范校验 + 前端构建三者全过；既有断言一条未挂。

### 步骤 5 · 跨端契约

后端用校验型 schema 作为数据结构事实来源。前端类型**优先用代码生成**（`openapi-typescript` 从 `/openapi.json` 生成）——手工对齐在字段变多后必然漂移。

字段变更必须两处同改：装配处塞值 **且** 响应模型显式声明。若模型配置为「忽略未知字段」，未声明的字段会被静默丢弃（白加 → 前端 undefined 但没人报错）。

**完成标准**：改一个字段后，前端用到旧字段的地方在**编译期**报错。

### 步骤 6 · 测试与闸门

校验脚本 + 总闸门。把约束写成断言，而不是靠人记。

需要机器拦截的（脚本已提供）：静态挂载顺序、比率列、事实表只增不减、裸 print、路径与端口硬编码、字号令牌、可读性、组件库规范。

需要单测锁住的：判定逻辑（口径、阈值、空值）、服务端与前端文案一致性、**修正层叠加后的聚合结果与修正前一致**。

**真浏览器实测**——只看构建产物只证明构建通过，不证明浏览器生效。常见两类假象：「构建过但页面没动」「图片 404」。

**完成标准**：闸门命令串成一条，全绿。

### 步骤 7 · 运维部署

**先判定部署形态**——不同形态的要求差别很大，别用一套配置糊所有场景：

| 需求 | 形态 | 关键前提 |
|---|---|---|
| 内部自用、本机跑 | 不部署 | 固定端口可以 |
| 局域网共享 | 单容器自托管 | 挂卷 + 读 `PORT` |
| 云上跑、要定时刷新 | 单容器自托管（**调度外置**） | 源数据只读挂载 |
| 快速演示 / 发链接 | 单端口发布 | 存储住在应用内（SQLite/JSON） |
| 多用户 / 并发写入 / 结构演进 | 托管后端 | **重新裁决数据层**（见步骤 2.5） |

> 详细机制、失败模式与检查清单见 `references/deployment-and-portability.md`。

**跨形态都成立的六条**：

1. **端口读环境变量**：`PORT = int(os.getenv("PORT", "8000"))`。写死端口是「本地能跑、云端起不来」的经典原因，且**构建期不报错**。
   > ⚠️ **容器入口命令必须读 `$PORT`**：`exec uvicorn app:app --host 0.0.0.0 --port "${PORT:-8000}"`。
   > `EXPOSE 8000` 在现代容器平台里**只是文档性声明，不决定实际端口**——平台靠 `PORT` 环境变量协商。
   > 入口写死 8000 → Cloud Run / K8s 注入 8080 → 健康检查探不到 → 流量进不来。
2. **路径从模块位置或环境变量推导**，不用绝对路径字面量。跨 OS 还要注意：路径分隔符用 `pathlib`、大小写（Windows 不区分、Linux 区分）、中文路径。
3. **数据与代码分离**：产物目录可配置、可挂载、可丢弃重建。
4. **数据库不进版本库**，且能从源数据重建。
5. **有健康检查端点**，且不依赖业务数据与源文件。
6. **日志走 stdout/stderr**（`logging` 的 StreamHandler），不写本地日志文件——云端收集的是标准流，写文件是双重故障（平台看不到 + 容器重建即丢）。

**本地自托管的补充**：

- **两套部署形态**：开发用 dev server 代理转发数据/图片请求到后端；生产构建后由同进程同源托管。代理目标写 `127.0.0.1` 而非主机名（新版本 Node 把 `localhost` 解析成 IPv6，后端只听 IPv4 → 整站 502，但命令行 curl 正常极具迷惑）。代理必须列全所有前缀，漏一个会让某类资源在生产正常、开发全裂。
- **入口 HTML 强制 `no-store`**：`/assets` 下的文件带内容 hash，可以长缓存；`index.html` 文件名固定，缓存它会导致「改了前端却看不到变化」——极难自查。
- **SPA history 回退 + 深链不 404**：直接访问 `/module/xxx` 这类前端路由要回退到入口页。
- **调度跑「工作区代码」而非固定 commit**：若用 CI/容器部署，改成「跑特定 tag/镜像」。**未提交的半成品会被当晚任务直接吃到** → 半成品不过夜。

**容器化的补充**：

- **多副本 × 容器内 cron = 定时任务重复执行**。要么固定副本数为 1，要么把调度外置到平台 Cron 调 HTTP 触发端点。
- **优雅退出**：收到 SIGTERM 时停接新请求、做完手上的活再退；用 `tini` 作 PID 1 回收僵尸进程。
- **数据目录声明为可挂载卷**，源数据目录**只读**挂载（数据源语义上只读）。

**不可逆搬移的安全流程**（三种形态都需要）：

- **默认 dry-run**：整理功能默认只读出清单与报告，零搬动。首次上线三步走：dry-run → 人工过目 → 转自动（只改环境变量）。
- **最小安全流程**（任何不可逆动作）：前置指纹落盘（源文件哈希 + 大小 + 目录清单）→ 断言前置状态防重复执行 → 执行 → 后置逐份核对（内容哈希 + 清单集合 == 实际集合 + 环境未被污染）。
- **回收站而非硬删**：逐个送系统回收站（可还原）；回收站不可用时只在报告里标记延迟，不硬删、不中断批处理。
- **公开仓库的业务数据禁入仓**：忽略配置 + 推送前扫描（忽略配置复核、密钥正则、外网硬编码、真实业务标识）。核验只能看远端主干。

**完成标准**：推送前闸门全绿（后端真导入 + 单测 + 前端构建 + 令牌校验）；`check_portability.py` 通过；健康检查端点可用；按部署形态核对上面的补充项。

### 步骤 8 · 工程治理

- **ADR**：非显然技术选型先写决策记录再动手。三条同时成立才写——① 难以逆转；② 脱离背景会令人费解；③ 真实权衡的结果。缺任一条就跳过（ADR 目录一旦堆满垃圾就没人读）。
- **接手规则文档**：集中写「怎么改才安全」「为什么不能这么动」，按「约束 → 为什么 → 怎么验证」组织。这是 AI 接手时最该先读的一份。
- **领域词汇表**：跨模块跨人沟通用词一致。
- **中文注释 + 英文标识符**；类与公开函数写文档注释；复杂逻辑写「为什么」；**⛔ 禁决策残留**（方案 A/B 只用一个，清掉另一个的痕迹）。

**完成标准**：ADR 与接手规则文档存在，且接手者能据此判断「这个改动安不安全」。

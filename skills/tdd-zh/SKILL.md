# 测试驱动开发（TDD）

TDD 是「红 → 绿」的循环。本技能是一份参考，让这个循环产出"值得保留的测试"：什么是好测试、测试放在哪里、有哪些反模式、以及循环的规则。每一节在每个周期都适用——在循环前和循环中查阅，而不是事后。

探索代码库时，先读 `CONTEXT.md`（若存在），让测试名称和接口词汇与项目的领域语言一致，并尊重你正在接触的区域的 ADR（架构决策记录）。

## 什么是好测试

测试通过**公共接口**验证行为，而不是实现细节。代码可以彻底改写，测试不应随之改写。好的测试读起来像一份规格说明："用户能用有效购物车结账"——它精确告诉你存在什么能力，并且能在重构后存活，因为它不关心内部结构。

示例见 [tests.md](tests.md)，mock 指南见 [mocking.md](mocking.md)。

## 接缝：测试放在哪里

**接缝（seam）** 是你在其上观察行为、而不必深入内部的公共边界。测试位于接缝处，绝不针对内部。

**只在预先约定好的接缝上测试。** 写任何测试前，先写下被测的接缝，并与用户确认。没有经过确认的接缝，就不写测试。你无法测试一切，所以提前约定接缝，才能让测试精力落在关键路径和复杂逻辑上，而不是每个边界情况。

问："公共接口是什么，我们应该测哪些接缝？"

当接口本身的形态存疑时（模块有多深、接缝属于哪里、接口该暴露什么），调用 Skill 工具加载 `codebase-design` 获取词汇表。它是「模块 / 接口 / 深度 / 接缝 / 适配器 / 杠杆 / 局部性」这些术语的唯一来源，是一个供查阅的参考，而不是要运行的一次会话。

## 反模式

- **实现耦合**：mock 内部协作者、测试私有方法、或通过旁路（直接查数据库而非走接口）来验证。特征：重构后行为没变，测试却挂了。
- **同义反复**：断言用与代码相同的方式重算期望值（`expect(add(a, b)).toBe(a + b)`、手工以相同方式推导的快照、断言常量等于自身），因此它靠构造通过，永远不可能与代码产生分歧。期望值必须来自**独立的真相来源**：一个已知正确的字面量、一个已验证的示例、或规格说明。
- **水平切片**：先写完所有测试，再写完所有实现。批量测试验证的是"想象中"的行为：你测的是事物的"形状"而非面向用户的行为，测试对真实改动变得不敏感，并且在理解实现之前就锁定了测试结构。应改用**垂直切片**：一个测试 → 一个实现 → 重复，每个测试都是一支响应上一周期教训的"试探子弹"。

## 循环规则

- **先红后绿。** 先写会失败的测试，再只写足够让其通过的代码。不要预判未来的测试，也不要添加投机性的功能。
- **一次一个切片。** 每个周期一个接缝、一个测试、一个最小实现。
- **重构不属于循环。** 重构属于审查阶段（见 `code-review` 技能），而不是红→绿的实现周期。

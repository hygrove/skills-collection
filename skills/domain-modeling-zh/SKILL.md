# 领域建模（Domain Modeling）

在设计过程中，主动地构建并打磨项目的领域模型。这是一门**主动**的功夫：挑战术语、设想边界情况场景，并在决策成型那一刻就把词汇表和决策写下来。（仅仅为了查词而**阅读** `CONTEXT.md` 不算本技能——那是任何一个技能都能做的一行习惯。本技能用于你正在**改变**模型、而不只是消费它的时候。）

## 文件结构

大多数仓库只有单一上下文：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果仓库根目录存在 `CONTEXT-MAP.md`，说明该仓库有多个上下文。该映射文件指出每个上下文所在的位置：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 系统级决策
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 上下文专属决策
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

**惰性创建文件**：只在确有内容要写时才建文件。如果还没有 `CONTEXT.md`，在第一个术语被敲定时再创建。如果还没有 `docs/adr/`，在需要第一份 ADR 时再创建。

## 会话过程中

### 对照词汇表进行挑战

当用户使用的术语与 `CONTEXT.md` 中已有的用语相冲突时，立即指出："你的词汇表把'cancellation'定义为 X，但你似乎指的是 Y。到底是哪个？"

### 打磨模糊用语

当用户使用含糊或过载的术语时，提议一个精确的规范术语："你说'account'：你指的是 Customer 还是 User？这是两个不同的东西。"

### 讨论具体场景

当讨论领域关系时，用具体场景来做压力测试。设想一些探测边界情况的场景，逼使用户把概念之间的边界讲清楚。

### 与代码交叉验证

当用户陈述某事的运作方式时，检查代码是否认同。如果发现矛盾，把它摆出来："你的代码会取消整个 Order，但你刚才说部分取消是可行的。哪个是对的？"

### 就地更新 CONTEXT.md

当一个术语被敲定，立即就地更新 `CONTEXT.md`。不要攒到一起再批量处理：边发生边记录。使用 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md) 中的格式。

`CONTEXT.md` 应当完全不掺杂任何实现细节。不要把它当作规格说明、草稿本或存放实现决策的地方。它只是一部词汇表，仅此而已。

### 谨慎提议 ADR

只有当以下三点同时成立时，才提议创建 ADR：

1. **难以逆转**：日后改主意的代价是实质性的
2. **脱离背景会让人费解**：未来的读者会纳闷"他们当初为什么这么做？"
3. **真实权衡的结果**：确实有过真正的替代方案，而你出于特定理由选了其中一个

如果三点中缺任何一点，就跳过 ADR。使用 [ADR-FORMAT.md](./ADR-FORMAT.md) 中的格式。

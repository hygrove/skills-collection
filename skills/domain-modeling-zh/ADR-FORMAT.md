# ADR 格式（ADR Format）

ADR 存放在 `docs/adr/`，使用顺序编号：`0001-slug.md`、`0002-slug.md` 等。

惰性创建 `docs/adr/` 目录：只在需要第一份 ADR 时才建。

## 模板

```md
# {决策的简短标题}

{1–3 句话：背景是什么、我们决定了什么、为什么。}
```

就这些。一份 ADR 可以只有一个段落。价值在于记录*做出了*某个决策以及*为什么*，而不在于填完各个栏目。

## 可选栏目

只有当它们确实增加价值时才包含。大多数 ADR 不需要它们。

- **Status 状态** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：在决策被重新审视时有用
- **Considered Options 考虑过的选项**：只有在被拒绝的替代方案值得记住时
- **Consequences 后果**：只有在需要点出非显而易见的下游影响时

## 编号

扫描 `docs/adr/` 找出已有的最大编号，加一。

## 何时提议一份 ADR

以下三条必须全部为真：

1. **难以逆转**：日后改变主意代价不小
2. **没有背景会令人惊讶**：未来的读者看着代码会纳闷"他们到底为什么要这么做？"
3. **真实权衡的结果**：确实存在真正的替代方案，而你出于具体理由选了其中一个

如果一个决策容易逆转，就跳过它：你大不了把它逆转回来。如果它不令人惊讶，没人会纳闷为什么。如果没有真正的替代方案，除了"我们做了显而易见的那件事"之外没什么可记录的。

### 什么算数

- **架构形态。** "我们用的是 monorepo。""写模型是事件溯源的，读模型被投影进 Postgres。"
- **上下文之间的集成模式。** "Ordering 与 Billing 通过领域事件通信，而非同步 HTTP。"
- **带有锁定性的技术选型。** 数据库、消息总线、认证提供商、部署目标。不是每个库：只是那些换掉要花一个季度之久的。
- **边界与范围决策。** "客户数据由 Customer 上下文拥有；其它上下文只按 ID 引用它。" 明确的"不做"和"做"一样有价值。
- **对显而易见的路径的刻意偏离。** "我们用手写 SQL 而非 ORM，因为 X。" 任何一位合理读者会假设相反情况的地方。这些能阻止下一位工程师去"修复"某个有意为之的东西。
- **代码中不可见的约束。** "因为合规要求，我们不能用 AWS。""因为合作方 API 契约，响应时间必须低于 200ms。"
- **当拒绝并不显而易见时，记录被拒绝的替代方案。** 如果你考虑过 GraphQL 并出于微妙理由选了 REST，就记下来；否则六个月后还会有人再提 GraphQL。

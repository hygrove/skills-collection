# 拆解为工单（To Tickets）

把一份计划、规格说明或对话拆解为一组**工单（tickets）**：示踪子弹式的垂直切片，每张都声明**阻塞**它的其它工单。

问题追踪器与分诊标签词汇本应已提供给你。如果没有，请告诉用户去运行 `/setup-matt-pocock-skills-zh`。

## 流程

### 1. 收集上下文

从对话上下文中已有的内容出发工作。如果用户作为参数传入了一个引用（规格说明路径、issue 编号或 URL），就去抓取并通读它的正文与评论。

### 2. 探索代码库（可选）

如果你还没探索过代码库，就去做，以了解代码的当前状态。工单标题和描述应使用项目的领域词汇表，并尊重你所触及区域的 ADR。

寻找机会预先重构（prefactor）代码，让实现更容易。"先让改动变得容易，再做那个容易的改动。"

### 3. 草拟垂直切片

把工作拆成**示踪子弹**工单。

<vertical-slice-rules>

- 每个切片纵向切穿每一层（schema、API、UI、测试）的一条又窄又**完整**的路径：是垂直的，不是某一层横向切片
- 一个完成后的切片自身即可演示或验证
- 每个切片的大小要能塞进一个全新的上下文窗口
- 任何预先重构都应先做

</vertical-slice-rules>

给每张工单标注它的**阻塞边**：在它开始前必须先完成的其它工单。没有阻塞项的工单可以立即开始。

**宽泛重构（wide refactor）是垂直切片的例外。** 一个**宽泛重构**是一次机械性改动（重命名一列、给一个共享符号改类型），其**爆炸半径（blast radius）**横跨整个代码库，因此单处编辑会一次性破坏数千个调用点，没有任何垂直切片能保持绿灯。不要强行塞进示踪子弹；把它编排成**扩展–收缩（expand–contract）**。先扩展：在旧形式旁边加上新形式，这样什么都不会坏。然后按爆炸半径分批迁移调用点（按包、按目录），每批是一个被"扩展"阻塞的工单，由于旧形式仍存在，批次之间保持 CI 绿灯。最后收缩：当没有任何调用方剩余，在一个被每个迁移批次阻塞的工单里删除旧形式。当连批次自身都无法单独保持绿灯时，保留该序列，但让它们共享一个集成分支，所有批次都阻塞一个最终的"集成并验证"工单；绿灯只在那里承诺。

### 4. 向用户提问

把提议的拆分作为编号列表呈现。对每个工单，展示：

- **Title 标题**：简短描述性名称
- **Blocked by 被阻塞于**：哪些其它工单（若有）必须先完成
- **What it delivers 交付内容**：这张工单让什么端到端行为跑通

问用户：

- 粒度感觉对吗？（太粗 / 太细）
- 阻塞边正确吗：每张工单是否只依赖真正卡住它的工单？
- 有没有工单应该合并或进一步拆分？

迭代直到用户批准该拆分。

### 5. 把工单发布到配置好的追踪器

发布已批准的工单。**如何发布**取决于 `/setup-matt-pocock-skills-zh` 配置的追踪器；工单本身两边一致，只有阻塞边的形态会变：

- **本地文件** → 在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 下为每张工单写一个文件，从 `01` 起按依赖顺序编号（阻塞项在前）。每个文件的"Blocked by"列出它所依赖的编号/标题。使用下面的每张工单文件模板：一张工单一个文件，绝不用单个合并文件。
- **真实问题追踪器（GitHub、Linear 等）** → 按依赖顺序（阻塞项在前）每张工单发布一个 issue，以便每张工单的阻塞边能引用真实标识符。若该平台有原生阻塞/子issue关系就用它；否则把每张工单的"Blocked by"设为那些阻塞它的 issue。除非另有指示，打上 `ready-for-agent` 分诊标签；这些工单在构造上就是可被 agent 拾取的。

沿**前沿（frontier）**工作：任何阻塞项都已完成（done）的工单。对于纯线性链，就是从上到下。

**不要**关闭或修改任何父 issue。

# 诊断 Bug（Diagnosing Bugs）

一套针对难啃 bug 的纪律。除非有明确理由，否则不要跳过任何阶段。

探索代码库时，先读 `CONTEXT.md`（若存在）以建立相关模块的清晰心智模型，并查看你正在接触区域的 ADR。

## 脱敏（Redact）

本技能会让你展示命令、输出和捕获的制品。**先把每个机密脱敏**：用 `<REDACTED>` 替掉。基于环境变量来搭建循环，这样凭证留在环境里，而不是留在你展示的内容里。捕获的制品带着鉴权头：只引用携带信号的那些行。

如果脱敏后的输出不足以诊断 bug，如实说明并向用户要更多。

## 阶段 1：搭建反馈环

**这才是本技能的核心。** 其余一切都是机械动作。如果你有一个对这个 bug **紧凑**的通过/失败信号（一个能在这个 bug 上变红的信号），你就能找到原因；二分、假设检验、插桩都只是在消耗它。如果你没有，盯着代码看再久也救不了你。

在这里投入不成比例的精力。**要 aggressive。要有创意。拒绝放弃。**

### 搭建方式，大致按此顺序

1. **会失败的测试** 在能触及 bug 的任意接缝上：单元、集成、e2e。
2. **Curl / HTTP 脚本** 打一个运行中的开发服务器。
3. **CLI 调用** 配一个固定输入，把 stdout 和已知良好的快照做 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer）驱动 UI，对 DOM/console/network 做断言。
5. **重放捕获的 trace。** 把一个真实的网络请求 / 负载 / 事件日志存到磁盘；在隔离中通过代码路径重放它。
6. **一次性测试台（harness）。** 起一个系统的最小子集（一个服务、mock 掉依赖），用一次函数调用就能跑到 bug 代码路径。
7. **属性 / fuzz 循环。** 如果 bug 是"有时输出错误"，跑 1000 个随机输入找失败模式。
8. **二分测试台。** 如果 bug 出现在两个已知状态（commit、数据集、版本）之间，自动化"在状态 X 启动、检查、重复"，这样你就能 `git bisect run` 它。
9. **差分循环。** 把相同输入分别跑旧版本 vs 新版本（或两种配置），对输出做 diff。
10. **HITL bash 脚本。** 最后手段。如果必须人来点，就用 `scripts/hitl-loop.template.sh` 驱动*他们*，让循环依然是结构化的。捕获的输出反馈给你。

搭对反馈环，bug 就修好 90% 了。

### 收紧循环

把循环当产品对待。一旦有了*一个*循环，就**收紧**它：

- 我能让它更快吗？（缓存设置、跳过无关初始化、缩小测试范围。）
- 我能让它信号更锐利吗？（针对具体症状断言，而不是"没崩溃"。）
- 我能让它更确定吗？（钉死时间、给 RNG 设种子、隔离文件系统、冻住网络。）

一个 30 秒、flaky 的循环比没有强不了多少；一个 2 秒、确定的循环才是紧凑的、调试的超能力。

### 非确定性 bug

目标不是一个干净的复现，而是一个**更高的复现率**。把触发器循环 100 次、并行化、加压力、收窄时间窗口、注入 sleep。50% flake 的 bug 是可调试的；1% 的不是，所以不断提高复现率直到可调试。

### 当你真的搭不出循环时

停下，明确说明。列出你试过什么。向用户要：(a) 能复现它的任何环境的访问权，(b) 一份脱敏的捕获制品（HAR 文件、日志 dump、core dump、带时间戳的录屏），或 (c) 添加临时生产插桩的许可。在**没有循环**的情况下，绝不要进入假设阶段。

### 完成判据：一个会红的紧凑循环

当循环**紧凑**且**能变红**时，阶段 1 完成：你能说出**一个命令**（脚本路径、测试调用、curl），它你**已经至少跑过一次**（展示调用和它的输出，已脱敏），并且满足：

- [ ] **能变红（Red-capable）**：它驱动真实的 bug 代码路径，并断言**用户的确切症状**，所以它能在 bug 上变红、修好后又变绿。不是"不报错就跑通"；它必须能*抓到这个具体 bug*。
- [ ] **确定性**：每次运行结论一致（flaky bug：按上面固定一个高复现率）。
- [ ] **快**：秒级，不是分钟级。
- [ ] **agent 可跑**：你可以无人值守地运行它；人在回路里只通过 `scripts/hitl-loop.template.sh`。

如果你发现自己在这个命令存在之前就在读代码建理论，**停下：直接跳到假设正是本技能要防的那种失败。** 没有能变红的命令，就没有阶段 2。

## 阶段 2：复现 + 最小化

跑循环。看着它在 bug 出现时变红。

确认：

- [ ] 循环产生的是**用户**描述的失败模式，而不是碰巧在附近的另一种失败。修错 bug = 修错东西。
- [ ] 失败在多次运行中可复现（或，对非确定性 bug，复现率高到足以拿它调试）。
- [ ] 你已捕获确切症状（错误信息、错误输出、慢的耗时），以便后续阶段能验证修复确实解决了它。

### 最小化

一旦红了，把复现缩到**仍然会红的最小场景**。逐个砍掉输入、调用方、配置、数据、步骤，**每次砍完重跑循环**，只保留对失败"承重的"东西。

为什么费这劲：最小复现缩小了阶段 3 的假设空间（剩下可被怀疑的活动部件更少），并成为阶段 5 里干净的回归测试。

完成标志：**每个剩余元素都承重**：去掉其中任何一个都会让循环变绿。

在已**复现且最小化**之前，不要继续。

## 阶段 3：假设

在测试任何一个之前，先生成 **3–5 个排好序的假设**。单假设生成会锚定在第一个看似合理的想法上。

每个假设必须是**可证伪的**：说出它做出的预测。

> 格式："如果 <X> 是原因，那么 <改动 Y> 会让 bug 消失 / <改动 Z> 会让它更糟。"

如果你说不出预测，那假设只是个感觉：丢弃或 sharpen 它。

**测试前把排好序的列表给用户看。** 他们常常有领域知识能瞬间重排（"我们刚给 #3 部署了改动"），或知道哪些假设已经被他们排除。便宜的检查点，巨大的省时。不要在上面阻塞；如果用户不在（AFK）就按你的排序继续。

## 阶段 4：插桩

每个探针必须对应阶段 3 的某个具体预测。**一次只改一个变量。**

工具偏好：

1. **调试器 / REPL 检视**，如果环境支持。一个断点胜过十条日志。
2. **针对性日志**，打在能区分假设的边界处。
3. 绝不要"记录一切然后 grep"。

**给每个调试日志打上唯一前缀**，例如 `[DEBUG-a4f2]`。结尾清理变成一次 grep。没打标签的日志会存活；打了标签的会死。

**性能分支。** 对性能回归，日志通常不对。取而代之：先建立基线测量（计时测试台、`performance.now()`、profiler、查询计划），然后二分。先测量，后修复。

## 阶段 5：修复 + 回归测试

在修复**之前**写回归测试，但仅当有**正确的接缝**可用。

正确的接缝是指：测试在调用点处复现了**真实的 bug 模式**。如果唯一可用的接缝太浅（bug 需要多个调用方却只有单调用方测试，或无法复现触发链路的单元测试），那里的回归测试只会给虚假信心。

**如果不存在正确的接缝，这本身就是一个发现。** 记下来。代码库架构正在阻止 bug 被锁死。把它标记给下一阶段。

如果存在正确的接缝：

1. 把最小化后的复现变成那个接缝上一个会失败的测试。
2. 看着它失败。
3. 应用修复。
4. 看着它通过。
5. 针对原始（未最小化）场景重跑阶段 1 的反馈环。

## 阶段 6：清理

在宣布完成之前必须做：

- [ ] 原始复现不再复现（重跑阶段 1 循环）
- [ ] 回归测试通过（或已文档化"无接缝"）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（grep 该前缀）
- [ ] 一次性原型已删除（或移到明确标记的调试位置）
- [ ] 最终被证明正确的假设已写在 commit / PR 信息里，让下一个调试者能学到
